# V25 serving precision and weight-adapter contract

**An unchanged247888 transplant is blocked. A WGS-only serving implementation is structurally feasible if it changes the dequantization scale domain and preserves Marlin's two BF16 GEMM-output roundings.** A packing-only adapter cannot do that. No GPU, candidate or model-loader edits were made for this review. Exact source hashes and the bounded NumPy arithmetic results are in `experiments/iterations/20261104-native-serving-v25-precision.json`.

The comparator is the actual H200 Marlin serving path at SGLang `a55ab7d5ae1bba59ac351e55026fe7f7644ecc5f`, not an idealized checkpoint equation or the native challenge reference. The challenge reference computes different FP32 intermediates, while its supplied Marlin baseline deliberately represents serving. A passing official native test alone would not establish serving compatibility.

## Actual loaded weights and legal adapter boundary

`MuseSparkNvFp4FusedMoEMethod` allocates canonical local tensors: gate/up codes `[L,2I,H/2]` with gate first, FP8 scales `[L,2I,H/16]`, global scales `[L,2]`, and corresponding down tensors. Its `_process_weights_for_marlin` aliases the canonical names, calls the stock conversion, and deletes the old native parameter names (`quantization/muse_spark_nvfp4_moe.py:116–140`). Post-load tensors therefore contain **Marlin layout and processed scales**, not the original native arrays expected by247888.

The stock base method collapses gate/up global scales to column0, warning if columns disagree (`modelopt_quant.py:2685–2711`). `prepare_moe_nvfp4_layer_for_marlin` then casts that global scalar to the activation dtype, BF16 for this target, and multiplies it by `2^119` in BF16 (`marlin_utils_fp4.py:47–58,514–515,563–568`). The original FP32 scalar and the discarded up scale cannot be reconstructed uniquely afterward. Target the **actual collapsed, rounded prepared scalar** for both halves; do not attempt to recover the discarded up scale or justify changing it by RMSNorm cancellation.

Two implementation boundaries avoid `model_loader` changes: (a) an explicitly selected serving backend branch inside this existing quantization preparation method, before stock repacking/deletion, or (b) a lossless inverse of the prepared local Marlin code/scale permutation. Option(a) avoids an unnecessary intermediate repack but must deliberately preserve the stock gate-column selection and BF16 global-scale processing. Respect the pre-existing interleaved-weight deinterleave branch if such metadata is accepted; otherwise decline before ownership transfer. Preparation should retain one selected native bank, replacing the Marlin payload after qualification, rather than retaining both full banks or247888's eight packed copies. A runtime fallback cannot call a Marlin kernel after its required bank has been discarded.

## The extra BF16 boundary the earlier scout missed

Marlin's actual CUDA `write_result` first executes `Dtype::float2num(c0/c1)`, then `__hmul2(res, global_scale)` for NVFP4 (`jit/csrc/gemm/marlin_moe/marlin_template.h:1533–1550`). With BF16 activation dtype this means:

`rounded_acc = BF16_RNE(FP32_acc); output = BF16_RNE(rounded_acc * prepared_global_BF16)`.

This occurs for gate, up **and down**. Merely adding a BF16 cast after the native FP32 product is insufficient. A reachable finite arithmetic counterexample uses normalized accumulator `1+2^-8` and effective BF16 global scale `1+2^-7`: two-round stock result is BF16`0x3f81` (1.0078125), while one final rounding gives`0x3f82` (1.015625). The same counterexample holds with the accumulator/global rescaled by `2^-119`/`2^119` as in Marlin.

Marlin's filtered SiLU subsequently reads those BF16 gate/up outputs, converts to FP32, computes `gate/(1+exp(-gate))*up`, and rounds that product to BF16. It does **not** take the separate activation-rounding variant (`activation.py:118–151,182–188`; `elementwise/activation.cuh:28–30,85–101`). H200's selected activation compile adds `--use_fast_math` (`jit/utils/arch.py:184–189`), while the actual Marlin GEMM uses default target flags without it (`ops/moe/moe_wna16_marlin.py:19–34`; `jit/utils/arch.py:114–137`). The serving core should not blindly inherit247888's global fast-math/FTZ flag after moving GEMM operands into the tiny Marlin domain: FP32 partial reductions could become subnormal. A concrete choice is ordinary non-FTZ GEMM/fixup compilation with explicit `__fdividef(gt,1.f+__expf(-gt))*up` in SiLU, followed by BF16_RNE. Actual compiler/device equality still needs validation. Preserve the existing pre-expert norm call before the native component (`muse_spark_fp4_moe.py:595–596`); folding it through GEMM weights is not an authorized equivalent transformation.

## Exact dequantization-domain design

Native247888 represents FP4 code values as BF16 `q*2^-126`, multiplies by BF16 `sf*2^64`, accumulates the resulting `q*sf*2^-62` operands, then compensates with `TWO62`. Marlin uses the same FP4 BF16 code representation, but its processed block scale decoder normally produces `sf*2^7`, so its operands are `q*sf*2^-119` (`marlin/dequant.h:393–406,476–488`; `marlin_moe/marlin_template.h:1243–1251,1275–1276`).

The clean serving design keeps the native packed code format and changes its scale pairs to the **exact Marlin-decoded BF16 bits**. For original positive-normal FP8 bytes`0x08..0x7e`, the normal PRMT bias becomes`0x3f803f80`, replacing`0x5c005c00`. Its LUT must be generated through the actual Marlin scale transformation, not simply `sf*128` for every byte. Then remove the `TWO62` epilogue compensation and apply the two BF16 roundings above with the already prepared global scalar.

There is a concrete subnormal exception. For original FP8 byte`0x01` (2^-9), stock preparation gives byte`0x68`, which its BF16 decoder maps to`0x0680` (2^-114), **not** mathematical`sf*128=0.25` (`0x3e80`). The direct formula disagrees for exactly bytes1..7 in the nonnegative finite domain; zero and bytes8..126 match. The source-derived CPU model checked119 normal scale encodings and2,032 code/scale pairs (16FP4 codes ×127 nonnegative finite FP8 bytes). For the exceptional seven bytes, the proposed LUT deliberately uses the stock-transformed bits. This is a finite arithmetic model, not execution of the actual CUDA helpers or proof of tensor-core handling of tiny BF16 operands. Negative/NaN scales need explicit stock-preserving qualification/fallback before replacing the weight bank; stock itself only warns about negative scales.

Changing only the final accumulator by`2^-57` would leave the native GEMM in a different operand domain. Matching the actual dequantized operands is preferable. **WGMMA versus Marlin's warp-level MMA still has a different FP32 reduction order and potentially different tiny-operand behavior.** The planned device comparison is therefore necessary even after byte-level operand proof.

Concrete scalar LUT generation from an original FP8 byte, omitting only the Marlin row/column permutations which the new packing owns: convert FP8→BF16→FP16 as stock preparation does; multiply by128 in FP16; reinterpret its16 bits, shift left1 with16-bit wrap, then take the high byte`b`. Decode the BF16 scale bits as `((b & 0x80) << 7) | ((b & 0x7f) << 4)` and duplicate that16-bit word into both lanes. Positive-normal entries may use the verified PRMT shortcut above. Global scalars should be the actual processed BF16 values converted exactly to FP32 for the existing scalar pointer ABI, not a reconstructed raw FP32 scale. For paired output accumulators a concrete epilogue is `__hmul2(__floats2bfloat162_rn(a,b), __float2bfloat162_rn(prepared_global_float))`; extracting gate/up lanes yields the FP32 inputs to SiLU. PhaseB stores this BF16 pair directly into its logical token/slot output rows, without norm weights or `TWO62`.

## Norm, combination and EP contract

Use the effective weight cached by `set_post_expert_norm`: `_get_effective_weight().detach().to(BF16)` (or BF16 ones), the actual epsilon, and the actual norm form (`muse_spark_fp4_moe.py:204–253`). Native247888 instead forms `1+raw_gamma` in FP32. These differ: gamma`[2^-8,0]` rounds to effective BF16`[1,1]`; with BF16 down values`[0.125,0.75]`, the two norm implementations produce different final BF16 first components,0.232421875 versus0.2333984375 in the two-column counterexample. Repeating each coordinate2048 times preserves this4096-column mathematical norm example.

The native finalizer also computes `(score*inverse)*y` and may contract accumulation, whereas the stock small-T eager path computes `(y*inverse)*score` before reducing slots. A finite FP32 example in the JSON differs by one ULP; this is not by itself a whole-output tolerance failure. The existing generic finalizer cancellation failure demonstrates why apparently equivalent reduction rewrites cannot be assumed safe. For the first serving-boundary experiment, keeping the **unchanged stock finalizer** and materializing the required BF16 expert outputs isolates the GEMM/activation port. A fused finalizer needs its own explicit norm-form/epsilon/mask and numerical validation; do not reuse the generic-failing helper as an unquestioned oracle.

The comment claiming exact RMSNorm cancellation of the collapsed up-scale gain is mathematically false when epsilon is nonzero and is further affected by BF16 roundings. With a constant row`y=1e-5`, gain2 and epsilon1e-8, normalization is approximately0.0995037183 versus0.196116135. Preserve the selected Marlin semantics instead of exploiting this claimed cancellation.

Use the real rank's `local_expert_offset` and `num_local_experts`, or its current exact map. Native247888 preparation hardcodes0/32, while serving EP8 can own any contiguous32-expert interval. Preserve original global IDs at the surrounding routing boundary, all eight slot weights, and every local duplicate route. Negative/nonlocal slots must follow stock masking. A rank can legitimately have no local jobs; the challenge's busiest-rank generator explicitly avoids that case, so its pass does not cover serving zero-job behavior. T0, arbitrary batches/chunks, scratch isolation across streams/graphs, and expert-TP/SP exclusions require explicit handling. No expert all-reduce can be deleted; it remains outside this local component.

The original stock finalizer safely excludes uninitialized remote expert-output slots: smallT first selects zero with`torch.where(ids>=0,x,0)` before arithmetic, while largeT skips their loads under`if live`. Therefore the core does not need an extra full-output zero fill if it writes every live output and the complete correct local-ID mask before calling that helper. Even an all-remote rank must produce the full mask and leave reusable workspace/counters valid. Do not simplify exceptional epsilon/nonfinite behavior; the unchanged helper remains responsible for it.

**Resolved split-reduction FTZ defect.** Removing global `--use_fast_math` was insufficient: the inherited WGS split path used `red.global.add.v4.f32`, whose global FP32 arithmetic flushes subnormal inputs and results independently of the compiler flag. Stock selected Marlin instead uses ordered `C_tmp` loads, ordinary FP32 additions, and stores in `global_reduce_fp32` (`marlin_template.h:1454–1506,1823–1829`; baseline selects `use_fp32_reduce=True`, `use_atomic_add=False`). A scalar partial `2^-127` has FP32 bits`00400000`, remains BF16`0040`, and after multiplying by prepared scale`2^119` yields0.00390625; a flushing reduction discards it. This is a source-semantic counterexample conditional on that partial being produced, not an observed tensor-core failure. [NVIDIA PTX9.0 reduction semantics](https://docs.nvidia.com/cuda/archive/13.0.2/parallel-thread-execution/index.html#parallel-synchronization-and-communication-instructions-red).

The author replaced that single active vector-reduction site with four integer `atomicCAS` loops using explicit `add.rn.f32` without `.ftz`. The initial read and retry compare bit patterns, so NaN equality cannot cause the classic floating-comparison retry bug. The four component addresses and the existing release/count/finisher protocol are preserved. This retains FP32 subnormal addition, but changes instruction cost and interleaving; neither throughput nor bitwise equality to Marlin's different reduction order is claimed.

**Resolved activation FTZ defect.** Stock H200 activation uses fast-math for its final FP32 SiLU×up multiply. Merely using explicit fast exponential/division inside an otherwise non-FTZ compilation did not preserve that multiply policy. The corrected code computes `silu=__fdividef(gt,1.f+__expf(-gt))`, then uses local `mul.rn.ftz.f32(silu,up)` before the BF16 store. The rest of GEMM/fixup stays non-FTZ. For illustration, CPU ordinary arithmetic with gate16 and BF16 up`0008` produces FP32`007fffff`, which rounds to BF16`0080`; the stock FTZ multiply flushes the up input and produces zero. This illustration does not certify CUDA fast-intrinsic output bits. For finite gate values the denominator is at least1: a subnormal division result is flushed by the final multiply, and a subnormal exponential cannot affect rounded `1+exp`. This closes the identified FTZ-policy gap without claiming all compiler/NaN-payload equivalence. [NVIDIA fast-math compiler options](https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/index.html#use-fast-math-use-fast-math).
