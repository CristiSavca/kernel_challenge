## Numerical requirements and resolved defect

Use scratch for **inverse RMS alone**, FP32 `[T,K]`; do not store inverse multiplied by route score. For weight-first, both passes must first form `f=float32(x)*float32(weight)`, and pass1 must reduce `f*f`. Pass2 must perform `f=f*inverse`, then `f=f*score`. Weight-after must perform `x*inverse`, then multiply weight, then score. `APPLY_NORM=False` ignores norm weights exactly as the parent does. No intermediate BF16 cast is allowed. Disable FP fusion initially so a separate score multiply and sum do not become FMA.

A small IEEE-FP32 shim gives a concrete regrouping counterexample: BF16 `x=15.875`, BF16 `weight=7.125`, `f=113.109375`, inverse `0.008841000497341156`, score `0.0538330078125`. Separate `float32(float32(f*inverse)*score)` rounds to BF16 `0x3d5c`; `float32(f*float32(inverse*score))` rounds to `0x3d5d`. The inverse is the shim's rounded H1 RMS inverse with epsilon1e-8. This is a finite rounding counterexample, not an actual Torch/Triton GPU output measurement or a universal rsqrt model.

**Resolved during review:** the original small path first replaces remote x with positive zero, then still executes normalization and score arithmetic. Skipping an entire invalid route or assigning it an arbitrary benign inverse changes exceptional behavior: `0*Inf`, a NaN norm weight, or zero epsilon can produce NaN in the parent. The revised plan masks only x loads and retains ordinary arithmetic for those zero slots. This avoids uninitialized remote reads and preserves the parent’s exceptional arithmetic without host tensor inspection. A purported finite-only fallback cannot be selected from tensor metadata alone.

The reduction tree, approximate rsqrt and handling of subnormals remain GPU numerical concerns. Sequential slot accumulation is mathematically correct but need not match Torch's reduction tree bitwise. Retaining FP32 operations and disabling fusion does not establish bit identity. The same applies to the norm sum/division. Check errors and final BF16 differences; retain the official reference gate.

Fastpath guards must use only ordinary metadata: CUDA BF16 x, T1..31, K1..32, H1..16384, and supported shape/device/dtype/stride contracts for auxiliary tensors. Preserve the original fallback for other cases and T0 early return. Scores and IDs may be noncontiguous; normalize or pass actual strides. A scalar/broadcast norm weight or score accepted by eager Torch must either be handled with its true strides/broadcast semantics or take the unchanged fallback. H padding contributes zero to the norm and divides by actual H; the final partial tile stores only valid columns. Do not inspect tensor values to choose the path.
