## Production-critical selection, capture and concurrency

The fastpath selects actual CUDA BF16 tensor metadata: nonempty T<32, top-k<=32, H<=16384, supported same-device auxiliary dtypes/shapes. T0 returns early; T>=32 uses the original fused kernel; unsupported small cases use the original Torch path. It is independent of request IDs, seeds, conversation content, load names and acceptance rates.

Pinned DFlash target-verify width is exactly the configured `num_draft_tokens=8` (`spec_info.py:290–300`, `spec_utils.py:96–122`). `model_runner.py:827–848` passes that width into the graph runner; `runner/decode_cuda_graph_runner.py:303–305,914–915` captures T=`request_bucket*width`. The environment default ragged mode is **static** (`environ.py:1419`); compact token tiers are a separate conditional mode, not assumed active. Therefore normal target-verify buckets1/2 give T8/16 and select the new path, while bucket4 gives T32 and buckets16/32 give T128/256, all unchanged. Runtime scheduler fill, graph padding, partial/eager passes and actual server environment must establish the real distribution. **Concurrency4 does not imply T4 or a new-path invocation.** Ordinary one-token decode or small prefill may still select it when those paths execute. Do not forecast four-load gains from the three component cases.

Production-critical local checks are H4096/K8, BF16 inputs and effective weights, FP32 scores/int32 local IDs, real post-norm epsilon, all-local/all-remote/mixed routes, T0/1/8/16/31/32 and representative larger control buckets. Warm kernels and the effective-weight cache before graph capture. Check captured T8/T16 replays with changing expert vectors, scores and local-ID masks; include transitions to T32 controls and ensure both new kernels appear only where selected. At K8 the new scratch is `32*T` bytes: 256B at T8, 512B at T16, at most992B in the small production domain. Generic max scratch3968B is not the production allocation.

Existing `.contiguous()` on expert output is retained; new `.contiguous()` calls for weights/scores/IDs are normally no-ops for this call chain but must be measured if an actual capture uses strided preallocated views. Metadata-only dispatch has no host read of route values. Two launches on the current stream order scratch publication. Each ordinary invocation owns new output/scratch tensors; there is no module-global workspace. This supports an ordinary current-stream implementation but does not itself prove capture or concurrent replay safety. Graph memory pools may deliberately reuse addresses between graph instances under a serial replay contract. Test independent graphs with disjoint inputs and pool ownership on separate streams, plus allocator reuse/repeated calls. Do not promise concurrent replay of the same graph/output buffers or unsynchronized mutation of shared input tensors. Preserve the caller's router side-stream wait and `record_stream` ownership at `muse_spark.py:874–884`.

Broader H/ragged/top-k/optional norm/dtype/strided/nonfinite checks are useful portable-helper coverage. They must not delay identification of an actual H4096/K8 graph failure, and passing them cannot replace rank-reduction or model-output tests. No production claim requires exotic NaN weights; preserving the old zero-slot arithmetic is nevertheless part of the generic helper contract.
