## One concrete hypothesis

**Keep the stock prefill front/back and replace only the grouped expert core with one full-batch, routed-row persistent W13→SiLU→W2 scheduler.** Retain the stock router’s global IDs/weights, actual local-rank mapping, pre-expert effective BF16 norm, finalizer and all attention/cache/residual computation. Build the per-expert counts/positions in the timed call; tile the actual local rows into 32–256 row groups and schedule by tile size. Store BF16 SiLU output in a compact expert-row layout and publish each tile’s completion before W2 consumes it. Gather BF16 route outputs back to `[T,8,4096]` for the unchanged stock finalizer in a first isolated version. No value-based host dispatch or fixed-route assumptions.

There is real reusable Apache-2.0 source, not just a paper: pinned [public prefill source](https://github.com/keell0renz/muse-open-kernel-challenge/blob/890809cee421500b00126d084e81b338ef9181ab/kernels/muse_prefill_layer.py), commit `890809cee421500b00126d084e81b338ef9181ab`, 370,116 bytes, SHA256 `f1807a75ec056b7f3874d4fce02331ca0043ac38a45af7710a8287a252421a92`. Relevant actual raw-file lines are `_repack`619–652, `_moe_forward`907–953, `consumer_item`3663–3981, `moe_fused_persistent`4274–4478, and plan/gather4480 onward. Its selected launch is 384 threads, one CTA/SM requested, 232,448 dynamic shared bytes; its register count is not measured here. Weight representation is one 864 MiB NVFP4 bank for 32 experts. Keep the [Apache license](https://github.com/keell0renz/muse-open-kernel-challenge/blob/890809cee421500b00126d084e81b338ef9181ab/LICENSE), NOTICE and existing vjeux/alygg77/ZhimaoL attributions if extracting code.

This is distinct from closed small-T WGS ring/register/SC6/private-partial experiments: it changes the **large grouped row algorithm** and fuses the intermediate activation into GEMM1’s epilogue. It does not eliminate either GEMM or their mathematical work. Relative to the baseline, keeping BF16 gate/up rounding in registers can avoid the global write and read of 8192 BF16 gate/up values: **32 KiB per computed local route**, before tile padding. That is a gross traffic saving, not HBM traffic measured or net benefit. New input gather, output scatter, padding, queue atomics and readiness waits consume work/traffic. A simple scatter-back costs another 16 KiB per local route (read plus write); no whole-kernel bandwidth forecast follows.

Scratch is not automatically smaller. Baseline `cache13+cache2` reserves `T*8*(8192+4096)*2` bytes. The donor’s three `[8T+8192,4096]` BF16 buffers reserve 0.3254/0.7390/3.1875 GiB at T753/3012/16384 versus baseline 0.1379/0.5515/3.0000 GiB, excluding other tensors. Thus a serving port must separately bound memory and replace old banks; merely adding the donor is not a deployment plan.

## Why unchanged donor import is a no-go

- The [README](https://github.com/keell0renz/muse-open-kernel-challenge/blob/890809cee421500b00126d084e81b338ef9181ab/README.md) reports an exact-file score of 1.9141, but also discloses a turn1/full misroute when state is first used from a fresh OS thread on the default stream. The repository’s top warning disclaims another current leaderboard entry. Neither its score nor a “fair” label substitutes for our source/rules review. The specific thread bug’s cause is not established here; the file has a module-global side stream and shared tuning state that should not be imported.
- Active `consumer_item`3890–3905 applies SiLU to FP32 scaled accumulators before one BF16 cast. The baseline materializes **BF16 gate and up first**. The donor also forms `1+w` in FP32 (`prepare`393–395; combine331–349), whereas stock norm modules supply effective BF16 weights. These are concrete semantic differences. Required adaptation must retain BF16 boundaries, actual prepared scale rounding and the exact effective norm; RMS normalization is not permission to cancel global scales/epsilon.
- Donor full-file changes also include different attention, dense tuning and residual recomputation. These are outside the isolated hypothesis. Its background compilation and global stream state are not needed for the extracted expert component.
- Publication must prove every W13 tile’s stores complete before the acquire that admits W2, with no queue deadlock when all resident CTAs reach dependent work; all-empty/local-remote/ragged/skewed routing and fresh stream/graph ownership need coverage. The source uses a dedicated publisher warp and release/acquire counters, but this review is not their correctness proof.

## Bounded next step and falsifier

Authorize a component extraction only after a focused review of weight/code/scale reconstruction, BF16 epilogues, full-range route grouping and the publisher protocol. Reuse V27’s *reviewed precision contract* as guidance, not its small-token scheduling or measured score. Keep all stock non-MoE paths unchanged and no attention/dense tuning sweep. CPU tests should establish reversible source scope, all route/rank/tile-boundary addresses, exact weight bytes, required BF16 casts, empty/skewed tile ownership and completion ordering models. GPU validation then needs five official tests plus all eight cases, adjacent shapes/page64, fresh-thread/default-stream and separate-stream/graph calls. Required official correctness tolerances remain unchanged.

The first private prefill check would establish both numerical viability and a whole-layer profile, not a claim of competitiveness. Reject if any precision/route/stream case fails, or if fused MoE plus its gather/scatter/queue time does not beat stock grouped Marlin on the same workload. Before submitting that candidate, root must freeze a useful weighted-load gain screen; no performance gate is retroactively selected here. If compiler/precision adaptation cannot fit preparation/time limits, stop rather than import the known problematic whole file.

No measured ceiling can be supplied without the MoE fractions. Conditional Amdahl model only: if fraction `f` of each stock load is this component and it speeds up by `g`, whole score is `1/(1-f+f/g)`. Matching today’s 2.1471 leader from stock through MoE alone would require about **4.22×/3.01×/2.46×** component speed at assumed f=70%/80%/90%, respectively. Those fractions and gains are unmeasured. Even the donor’s claimed full-file 1.9141 would need another 12.17% score improvement (10.85% latency reduction) to match the current leader. The high-value relevance is future serving TTFT, not a shortcut to overall #1 before the deadline.
