# Native DFlash depth and target verification width

V64 averaged 4.0, 4.0, 4.0 and 4.2 committed tokens per target pass at 1, 4, 16 and 32 users. These are published rung averages. They do not provide the probability of accepting the entire block or measurements for V84a. V64’s end-to-end score was 1.4119. [Judge result](abd217baf0ed49fd.json)

The native checkpoint predicts seven successive positions from one anchor. The selector scores 16 alternatives per position and conditions each edge on the preceding selected ID. Giving the target twelve or sixteen rows while the draft keeps width eight would add breadth. Even an optimal tree fed exclusively by this lattice can commit at most eight tokens in a target pass, including the target’s bonus token. Against the V64 rung means this bounds the improvement from acceptance alone at 2.00×, 2.00×, 2.00× and 1.90×, before any increase in step time. Wider physical target trees also cost more model work. ## Bounds for a longer continuation

Suppose the first seven proposals stay identical to the incumbent linear chain, and a new source proposes L more tokens after complete acceptance. If the probability of accepting the original seven is q, the expected gain cannot exceed Lq. Since an iteration that reaches the end commits at least eight, a measured mean A gives q ≤ (A−1)/7. At A=4, a perfect four-token tail can increase the mean by at most 1.71 tokens, for at most 1.43× decode at equal iteration cost. An eight-token tail has an optimistic maximum of 1.86×. The bounds assume unchanged first-block proposals, and are not limits on algorithms that also improve early-position acceptance.

For illustration, fitting a constant conditional match probability solely to A=4 gives p=0.787 and a full-block match probability of 0.186. Extending the same match probability from seven to fifteen proposals increases the expected number committed per iteration by 14.7%. For A=4.2, that estimate is 17.3%. Without observed acceptance histograms, these fits cannot predict performance. Broader trees can improve early acceptance, which is a distinct lever.

## A feasible implementation boundary

V84a uses the same physical width for the noise block, per-request draft graph, target verify graph, prepared KV slots, logit/bonus buffers and reported scheduler stride. Its tree kernel also derives the lattice row stride and expansion depth from the number of output nodes. V79a’s two attention bands already cover a twelve-row target at GQA8. To keep the native draft width, separate the lattice depth from the target node budget, allocate target slots at the target width, and pass only the native-width view to draft forward. Target attention and slot permutation must consume the entire target width. The draft context writer must consume every committed row after target verification, even when a different proposal source extends the path beyond the native depth. A separate graph configuration or path is needed for linear verification, including grammar, non-greedy sampling and requests requiring logits. [V84a patch](../candidates/v84a_routed_decode_committed_context/patch.diff), [V79a patch](../candidates/v79a_wide_selector_tree/patch.diff)

For exact greedy advancement past the native depth, a second source can attach ordinary proposed tokens beyond the final model-produced node. One option is direct suffix matching against the current request’s already-available token history, with hard bounds on lookup length and no cross-request state. This requires the runtime to expose the relevant token IDs to the proposer. The target evaluates every node at its exact logical position with its own ancestor mask. Walking target predictions and committing the bonus then gives the ordinary greedy stream by induction, regardless of proposal quality. No context, model output or prefix suggestion should be retained across requests for this purpose. The benefit depends on full native matches and repeatable continuations. There is no measured hit rate for this candidate. [Existing tree accept, slot permutation and graph interfaces](../candidates/v84a_routed_decode_committed_context/patch.diff)

A second normal DFlash block depends on projected target activations for the preceding committed rows, including layers 1, 16, 30, 44 and 59. Those activations for the new proposals become available only after executing target layers. Substituting stale or fabricated activations would change the draft computation. Running the second block after the target produces them introduces a second target sweep to advance beyond its position. V79a already provides a separate experiment in extrapolating a single wider draft block while preserving full target verification. Its cost and acceptance are unmeasured. [Draft projection and verification](../candidates/v84a_routed_decode_committed_context/patch.diff), [V79a validation](../candidates/v79a_wide_selector_tree/validation.json)

The available measurements support prioritizing target-step cost reductions alongside tree experiments. A 3× result requires a measured throughput gain across the concurrency frontier, with first-token latency, accuracy, request lengths and memory inside the official limits.
