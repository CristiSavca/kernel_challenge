# V193 scheduler and cache timing study

At 16 and 32 users the archived eight-H200 V41 requests spent much of each cold first turn waiting for prefill. Removing every later-turn first-token delay in those traces, including model and network work, gives a **1.031× and 1.032×** throughput ceiling if all other observed durations stay fixed. The 16-user trace attributed 1,231,675 of 1,415,564 actual prefill rows to cold turns. The 32-user trace attributed 2,460,293 of 2,825,080 rows to them. These counts reconcile with the scheduler’s logged prefill inputs. The 92% reported cache-hit rate includes repeatedly reused long prefixes in its numerator and gives no breakdown by host and device. ## An exact host-side opportunity

On ordinary TP8, PP1 serving, the scheduler broadcasts the inbound pickle length, even for an empty inbox. Within the same loop its HiCache poll reduces two acknowledgement counts and both signs of the reclaim digest, including when the local queues are empty. A single CPU MIN on four int64 values can transmit the leader’s negative message size, the minimum of every rank’s cache-clean flag and both signs of the digest. When there is no message, no deferred control or abort, no outstanding or queued transfer on any rank and the digests agree, the second collective has no effect. A production integration would preserve the ordinary payload broadcast and native cache checks on a veto, nonempty payload or digest mismatch. It must restrict the shared collective to the exact same CPU group and to native cache-only PP1 operation. Empty inbox alone does not establish eligibility. The prototype exercises the consensus contract independently of SGLang’s live state machine. Real 2-, 4- and 8-process CPU Gloo tests passed 102 message-size, asymmetrically dirty queue and divergent-digest combinations. The eight-process Mac loopback medians were 1.394 ms for the native empty broadcast plus cache MIN and 1.123 ms for one MIN, with a 0.490 ms median paired difference over ten alternating trials. V68’s four accepted tokens and 48 median per-user streaming tokens/s imply an 83.33 ms verification interval. A 5% fixed-interval gain would require 3.97 ms of *exposed* time per eligible verification. Neither the hardware archive nor the challenge status records an H200 host-poll stall of that size or the actual eligible clean-round frequency. The local comparison is sufficient to deprioritize the integration pending processor-side profiling on a permitted real node. ## Where to spend the next experiment

V41 had 75 full 16,384-row prompt launches at 16 users and 149 at 32. Improving the normal long-prompt kernel or overlapping compatible prompt work has much more exposed time in these traces. Direct GPU-resident prefix hits already return physical slots, host restores start before extend on a dedicated stream and emit readiness per layer. V134 covers pressure-only write-back, V154 covers reducing small host backup copies, and V160 covers mixed target scheduling. The observed full-pool usage peaked at 0.04/0.11/0.41/0.79 across the four loads; the logged formula excludes evictable rows, so these peaks cannot establish a count of H2D restores. V193 is a reproducible experiment with no contestant export.
