# V261 stages live expert rows while building the grouped decode plan

V261 removes one GPU launch per MoE layer from eligible target decode and verification. The original Humming path first sorted the route IDs and published a plan. A second kernel read that plan to gather BF16 input rows for W13. V261 computes the same metadata and writes those input rows in one kernel. At 62 layers this changes 124 planning and staging launches to 62 per eligible target forward on each rank. The code applies at up to 256 route slots and hidden widths from 1,024 through 4,096. Larger and smaller-width inputs retain the two-launch path. End-to-end speed, peak memory and token agreement on H200 remain unmeasured. [Full official export](patch.diff) · [One-file change from V256](delta.diff) · [Geometry](work.json)

The metadata CTA executes the original plan, including the values in its unused prefix. Every other CTA handles one original route. It reads that route's global ID and optional expert map, and exits if the result is remote or invalid. For a local route, it counts the valid routes with a higher local expert number or with the same expert and an original position at or after its own. Subtracting this count from the real slot count gives that route's unique position in the original stable-sorted suffix. It copies the corresponding token's BF16 payload there. These CTAs share no intermediate writes. The kernel completion supplies the dependency for W13 and leaves unused staging rows untouched. ## Reach and overhead

For top-eight routing, a plain target decode of up to 32 rows is eligible. A width-eight DFlash target verification is eligible at captured request capacities one through four. A combined speculative batch that runs on the ordinary prompt path follows its existing prompt implementation. Applying the width-eight shape test to the ending occupancies of 147 archived V41 scheduler reports selected 108 snapshots. Those reports sample occupancy and do not count actual forward invocations. [Historical geometry and caveats](work.json)

At the archived standalone H200 histogram of 32 rows, 39 of the 256 routes were local to the recorded rank. The fused schedule issues 256 scalar ID reads and 9,984 logical ID lanes for the suffix ranks. With int32 IDs and an int32 map, this is 81,920 logical bytes of additional ID and mapping reads if every global ID is valid. Their unique input storage spans at most 2,048 bytes. The two-launch gather formerly requested 668 logical bytes of first-offset and row-key reads. BF16 staging still has 638,976 logical bytes of reads and writes in either version. For 256 all-local routes the prospective extra int32 metadata reaches 526,336 bytes. Actual cache traffic, memory transactions, CTA scheduling, the slowest metadata CTA and the duration of a previously separate graph node determine the result. At 256 slots the fused launch has 257 CTAs, compared with one planner CTA and 128 gather CTAs in V256.
