# V249 · Private DFlash KV on target-owned sliding-window pages

V249 places all five BF16 draft layers in a smaller private KV pool whose physical rows follow the target sliding-window allocator. At V68's measured 16-user capacity this removes **6.116 GiB of logical draft KV payload per GPU**. The additional native FlashAttention graph tables at the archived dimensions consume about 48 MiB per rank. ## Ownership and allocation

When a CUDA BF16 draft uses FA3 or FA4, the worker checks the actual layer masks, shared request table and static target allocator. Every draft layer must use a bounded attention window no larger than the target's retained window. A fresh draft-only config requests a native `SWAKVPool` with five SWA layers and zero FULL layers for the published model. Its storage is separate from the target K/V tensors. Its full-to-SWA address table is the target allocator's actual mutable tensor. Unsupported backends, complex topology, compact mode, unified memory, remote backing, PD-Mux and unfamiliar allocators/layers keep their original allocation. The allocator continues to size target capacity using the parent's conservative charge. [Implementation](delta.diff) · [Eligibility and native allocation replay](replay.json)

Every target-hidden projection still executes. Native `KVLocPlan` resolves draft writes in the sliding-window address space. Sequential, fused and prefix-valid fallback stores use that physical bank exactly once. Native FA3/FA4 maps the page table and speculative writes into the same space. An earlier radix checkpoint can expose positions inside the previous chunk. Preserving all writes makes those rows available. During locked-FULL recovery the radix cache moves the fresh SWA ownership to the retained FULL IDs. The new request then reaches the private draft rows through the same mapping. A differing batch or recomputation schedule could still produce floating-point variation on hardware. [Earlier failure cases](../v243_draft_prefix_coverage/README.md) · [Address and host tests](replay.json) · [Independent graph and branch replay](independent_fa.json)

The existing HiCache draft registration recognizes the SWA pool and attaches a separate DRAFT_SWA host sidecar. The backup and restore plans reuse the target SWA transfer's device/host indices. At V68's recorded host slot counts the **logical** draft payload decreases by about 40.64 GiB per rank. Shared/pinned host backing, allocator rounding, transfer frequency, actual resident bytes and final serving capacity need measurement. Eager and graph metadata can translate a full-width table even for a short effective window. The V188 bounded-table optimization currently declines SWA-backed pools.
