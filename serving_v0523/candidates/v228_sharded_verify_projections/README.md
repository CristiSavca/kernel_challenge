# V228 output-column sharding for captured Hopper verification

V228 lets the tensor-parallel group divide two replicated BF16 projections in the Muse target. Each rank projects a contiguous slice of the output columns over the complete input dimension and gathers the finished columns in rank order. At 128 verification rows on TP8, the two matrices require **16 MiB of nominal weight reads per rank per layer**, down from 128 MiB. Across 62 sparse layers the difference is **6.78 GiB per rank per target pass**. The original full matrices stay resident for prompt processing. At eight rows the existing SM90 multicast path can already shard the output projection. The incremental weight-read reduction there is **3.39 GiB** when native multicast qualifies. [Code delta](delta.diff) · [Work model](work.json)

The ordinary TP all-gather transports the BF16 result directly. It adds a collective and a rank-major to row-major rearrangement for each newly sharded projection. V228 preserves the original router, expert routing order, expert all-reduce and any already eligible native multicast projection. The activation criterion compares the input width with the current row count. A single Gloo vote before each full capture epoch checks the loaded weights, topology, replay backend, hooks and determinism settings on all ranks. A fresh static batch carries the decision into the captured model. Eager inference uses V224’s dispatch. Views refer to the original weights, with no cached parameter copy. [Admission and ownership review](independent_review.md)

On the H200 standalone projection board, the full 128-row pooler and unpooler took 29.232 and 23.920 µs respectively. Taking V64’s acceptance and median decode rate as a verification-period proxy, the local GEMMs and both gathers would need to finish within **32.50 µs per layer** to improve this proxy by 1.63%. Router overlap can leave less time available. This comparison has no distributed measurement of V228.
