## Prefix retention and capacity

In all **708 V41** and **36 V44** later requests the reported cached token count equals the preceding turn’s prompt length plus one, across all recorded concurrency levels. The length evidence shows no loss of preceding prompt coverage as concurrency rises. The remaining previous-completion length equals the previous completion length minus one. The archive retained the combined cache count only. Native SGLang maintains separate device, host and storage hit counters. Neither client counts nor rounded full/SWA token usage resolve whether an individual prefix was restored. Full token usage omits evictable rows, so its 0.79 peak at 32 users cannot prove absence of eviction. ## Which cache intervention merits a measurement

The unmeasured cache intervention with access to the cold critical path is avoiding or shortening initial write-through backups. Native write-back already defers the backup until eviction. V154c already coalesces contiguous small destination pages without changing eviction policy. A separate path that batches fragmented small destinations would require actual destination-run histograms, evidence of exposed host submission time and a duplicate-destination ordering proof. Physical replay supplies none of those. This investigation produced no new serving patch or launch. [Native write-back control and guard checks](../../runs/v134_hicache_control.md) · [V154c transfer candidate](../v154c_v64_hicache_backup/README.md) · [Pinned batch-copy gate](../../sglang/python/sglang/kernels/jit/csrc/kvcacheio/staged_write_back.cuh)

For sensitivity, backing every V41 /32 logical row once in all three page-one pools would move 53.81 GB per rank. If each page needed separate K and V copies, that would mean 17.52 million small copies. A 2× result would require eliminating 152.215 seconds, or 8.69 μs of **exposed** time per such copy. For 3× the requirement is 202.953 seconds and 11.59 μs. SWA backs selected radix nodes, copies may coalesce or overlap, and actual backup counts may differ in either direction. The three pool widths, 4,096, 11,776 and 2,560 bytes per rank per token, describe the archived private full-draft layout. A future SWA-owned private draft needs new accounting. [Per-rung conditional exposure](trace.json) · [Pool byte derivation](../../runs/v134_hicache_control.md)

A discriminating private experiment would pair the same service and cold inputs under native write-through and write-back. Record per-tier hit rows, D2H/H2D bytes, page-run histogram, driver submission time, per-layer wait time and copy/compute overlap. A large D2H byte count with unchanged cold wall time would reject transfer-volume savings as an explanation for a multiplier. An increase in deferred eviction waits at 32 users would count against write-back. Production dispatch should use only native allocator state and ordinary model inputs. The archived request sequences serve solely as analysis evidence. [Serving rules](../../RULES.md)

## Time budget for the 4× target

Moving from V64's measured 1.4119× to 4× would require a further 2.833× under uniform gains across the four frontier points. On the *separate* V41 trace, a 2.833× reduction in elapsed time at 32 users would require the first wave alone to run 1.98× faster even if everything after it took zero time. If the later phase doubled in speed, the required first-wave factor would rise to 3.45×. At 16 users those two requirements are 1.83× and 3.67×. This calculation uses the observed first-token boundary and holds request work fixed. Improvements can differ across loads because the official score is a geometric mean. [Phase arithmetic and assumptions](trace.json) · [Official scoring](../../RULES.md)

The objective also needs gains across loads. If only two of four frontier points improve, each of those two would need a further 8.03× beyond the V64 frontier to reach 4× overall. Quadrupling just those two points gives a four-load score of 2.8238×. These two calculations follow directly from the published geometric mean. [Score arithmetic](trace.json)
