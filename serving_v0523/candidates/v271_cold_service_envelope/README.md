# V271 prices the cold serving wave and expert redistribution

The 32-user V41 cold wave took 212.780 seconds on eight H200s. It processed 2,455,793 new prompt rows and reused 4,500 cached rows. Replaying those requests with the V68’s sequence-parallel target and V268’s sharded long-prompt draft geometry gives 26.88 seconds of mean-rank useful BF16 matrix work and 3.82 seconds of target attention at ideal dense tensor-core rates. Expert gate/up/down contributes 15.49 seconds of the BF16 figure. The 30.70-second total prices selected arithmetic at peak. The actual V41 run used different code. Routing, tails, dequantization, collectives, normalization, draft operations beyond context projection, transfers, allocator costs and host time all affect the observed latency. These aggregates leave the largest exposed component of captured Humming unidentified. [Per-window work and source hashes](audit.json) · [Official V68 check](../../runs/04b01f958aa5487c.json)

The tensor counts include the output gate in the QKV projection width of 2,304 per rank and the attention output projection from 1,024 to 8,192. The 16 full-attention layers see 101,082,372,214 causal pairs per head. The 46 sliding layers see 4,971,264,218 pairs per head, including cached keys visible to new queries. Each rank computes 16 heads of width 64. Mean expert work includes one local route per global prompt row because there are eight selections and eight owners. A full packed 32-expert bank is 864 MiB per layer. One pass over 62 such banks is 52.31 GiB per rank, equivalent to 11.70 ms at 4.8 TB/s. At a uniform 16K chunk, the expert arithmetic alone is equivalent to 103.34 ms per 62-layer pass at 989.5 dense BF16 TFLOP/s. Physical HBM traffic depends on tile repetition, caches, precision conversion and non-weight tensors. The logical throughput denominator for this whole V41 window includes all 34,360,576 prompt rows, of which 31,535,496 were cached, plus 94,370 output rows. Only uncached rows enter the prompt-projection calculation. If the draft FC were replicated across ranks as on the earlier path, add 1.46 peak-equivalent BF16 seconds in this 32-user wave. ## What moving work to quieter ranks could buy

Four archived H200 single-rank runs timed the same 16,224-route input. The median complete stock Marlin call scales to 7.290 ms at 16,384 rows under a linear row-cost assumption. The best-case balanced BF16 work prices at 1.667 ms. A separate correctness fixture forced one rank to 30,697 routes, or 1.874 times the mean. It did not time this case or retain the other seven ranks. This isolated fixture establishes neither the critical rank nor sustained service skew. The historical prepared dense control ranged from 2.643 to 2.698 ms before dequantization, routing and finalization. [Single-rank data](../v186_hot_expert_row_splitting/check.json)

The first counterfactual below assumes the critical rank runs at 1.874 times the mean cost on every cold layer. A perfect placement balances it at the original mean with zero copy, dispatch or return cost. The second starts at the mean and reduces the entire expert call to the dense BF16 work floor. Both scale each repetition's cold request TTFT by the saving implied by its actual uncached demand and first-wave wall time. The demand, client gaps, remaining per-user phases and four official stock anchors are preserved. V41 phase fractions are transferred onto V64's measured rung rates. These are scenarios for the V64 frontier. V64's official 32-user first-turn p90 was 110.0 s. Individual requests and a same-run critical-rank profile are unavailable. [CPU replay](audit.py) · [Official V64 result](../../runs/abd217baf0ed49fd.json)

| Conditional cold change | 32-user first wave saved | Four-load score with later phases unchanged | If both later phases run twice as fast | If later phases take zero time |
|---|---:|---:|---:|---:|
| Current cold time | 0 s | 1.412× | 1.949× | 2.727× |
| Rebalance the forced skew at every layer | 59.18 s | 1.776× | 2.556× | 3.811× |
| Run the mean historical experts at peak BF16 | 52.25 s | 1.727× | 2.466× | 3.643× |

For the uniform improvement on both score axes that reaches 3×, shortening the 32-user cold phase by the same factor would require saving 10.18 ms per equivalent 16K sparse layer. The 4× scenario requires 12.91 ms. Using the historical mean cost, perfect redistribution alone would need a sustained critical/mean ratio of 2.40 or 2.77 respectively. A rank can be that overloaded in principle. An actual opportunity of that size needs simultaneous counts, durations and window counts from all eight peers. Even in the forced-skew scenario a 3× modeled frontier requires later TTFT and streaming each to run 3.39 times faster. [Conditional score calculations](audit.json)

The remaining system-level opportunity is to accelerate cold work in multiple operator families alongside later serving. One way to choose the family is to measure each layer's paired GPU events for the pool/router, expert windows, output collective and fixed-cost attention projections, after graph warmup on the same node. Join each event to rank ID, live routed rows, graph geometry and request phase. A long collective on a rank that finishes GEMM early can be a wait for the slowest expert owner. A synchronized caller time on its own cannot distinguish that case. First requests in this archive already received small real prefix hits. Later turns reused the previous turn's entire prompt plus one output token, with no timed restore or evict event visible on TP0. More unmeasured cache reuse or a new expert placement has no defensible numerical claim to 4× in these records.
