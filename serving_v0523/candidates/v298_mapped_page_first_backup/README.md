# V298 transfers large page-first KV backups in one kernel per pool

V298 changes the write-through path on the passing V68 serving configuration. For a large backup with distinct ascending host slots, the existing native CUDA transfer kernel can write all K and V layers straight into registered host memory. On an illustrative 16,384-row backup of all three published pools, this replaces 768 relayout kernel launches and 98,304 per-page CUDA copy calls with three all-layer KV kernels and three small index uploads. The 288 MiB of cache data per rank still travels to the host. Actual H200 submission cost, exposed stalls and serving throughput remain unmeasured. ## Which backups qualify

The MHA pool keeps its original page-first host layout, all staging buffers and the native transfer stream. On startup it verifies that the registered K/V tensor has one linear address mapping on the specific CUDA device that will issue the writes. It checks the returned device address at every independently registered range and verifies that the ranges cover the entire host allocation. A constant nonzero difference between host and device addresses works. A missing address resolver, a registration gap, disjoint device mappings, or an unregistered or managed allocation without these registration records selects staging. The production resolver uses CUDA's device guard and `cudaHostGetDevicePointer`. GPU peer access is unnecessary for this path. CUDA documents distinct device aliases for some registered or write-combined host allocations. [Initialization replay](startup.json) · [Registration tests](replay.json) · [CUDA unified addressing](https://docs.nvidia.com/cuda/cuda-runtime-api/group__CUDART__UNIFIED.html)

Only an already-supported CUDA JIT on packed device rows and page-size-one staging can enter the new branch. At submission, the CPU host index array and device source index array must be equally sized contiguous int64 vectors, and the transfer must span at least two staging batches. The CPU checks that destinations increase strictly before launching independent stores. Reversals, duplicates and strided arrays use the original ordered DMA path. The rank's existing transfer engine fences against the writing forward and records the host-ready event after the KV kernel. Native per-layer H2D restores, tree locks and acknowledgement processing retain their existing ordering. [Pool and transfer replay](replay.py) · [Pinned ordering checks](exposure.py)

## What the historical runs establish

Six single-user cold turns in V41 and V44 used 36 real prompt forwards. Thirty were unfinished 16,384-row chunks followed by a continuation. All six conversations began after a cache flush, had zero cached prompt rows, and spent 46.141 seconds in aggregate before first text. The continuation path retains its request and advances its prefix length without invoking host-restore admission. A new unfinished checkpoint can still issue a write-through backup to host memory. These archives used page-one, page-first kernel I/O with write-through enabled and metrics disabled. They give no per-pool backup counts, slot ordering, CUDA submission durations or copy/compute overlap. V68 also prepared the three staging pools. Its private check reports aggregate rungs. The 288 MiB case needs 4.72, 9.44 or 18.87 ms at assumed directional transfer rates of 64, 32 or 16 GB/s. The actual bytes and rates can differ. At the 1.2311-second V44 mean for matched isolated 16K chunks, a twofold chunk improvement from this backup alone would require 6.26 µs of eliminated, exposed work per original small copy. A fourfold improvement would require 9.39 µs. Across 41 alternating single-thread host trials with CUDA calls stubbed, Python dispatch took a median 1.291 ms for the three staged wrappers and 0.040 ms for the mapped branches. The large remaining question is how much time the real scheduler spends inside CUDA, including device backpressure. The new path also uses two CUDA blocks for the copy, so available PCIe throughput and contention with target computation matter. The 2× and 4× service targets remain open. ## Verification

The production pool initialization replay exercised 15 configurations. The ordinary transfer dispatcher, staged fallback and per-layer restore checked 82,612,480 bytes across 12 cases. A separate host compilation ran the real native CUDA worker and lane-address loops for 72 32- and 64-bit, 128- and 256-byte geometries and compared 533,667,840 bytes including untouched gaps. CUDA 12.9 compiled the 128- and 256-byte transfer wrappers for SM90a. Their four device images contained no local load/store instructions. Physical mapped-host visibility, native device addresses, memory peak, token correctness and end-to-end latency require an H200 run.
