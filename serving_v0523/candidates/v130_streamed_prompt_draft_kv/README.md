# V130 streamed draft KV materialization for long prompts

**Withdrawn and unscheduled.** The complete eight-row prompt path reuses a prefix-valid KV writer with different physical-slot semantics from the ordinary BF16 prompt writer. In a direct test of the frozen code, V130 replaced 64 bytes at reserved V slot zero, which the native writer preserved. At slot nine in a pool with logical capacity nine, the native writer raised its bounds assertion. V130 overwrote a guarded extra row. These failures invalidate this patch as a full-prompt optimization. V133 implements the ordinary writer’s reserved-slot and bounds checks. [Executable witness](reserved_slot_witness.py) · [Results](reserved_slot_witness.json) · [V133 independent review](../v133_direct_prompt_draft_kv/independent_review.md)

V130 bounds the size of draft intermediates during long prompt appends. For 16,384 tokens in the served model, the dense context projection and normalized context each occupy **256 MiB per rank** in V64. V130 processes four 4,096-row slabs, each occupying **64 MiB** for that intermediate. It still evaluates all five target taps and every prompt row, including rows beyond the current draft attention window that may be reused through the radix cache. The allocation figures are estimates. This artifact has no H200 measurement. [Official V64 score](../../runs/abd217baf0ed49fd.json) · [Frozen V130 export](patch.diff)

## The projection V64 already fuses

At initialization, SGLang's `FusedKVMaterializeHelper` extracts each layer's K/V weights from QKV, stacks the five local banks, and transposes the result once. At runtime **one** `torch.mm` produces all five layers' raw K and V for the supplied context rows. The native norm/RoPE kernel then processes the five layers together. The serial per-layer projections are a compatibility fallback. The public checkpoint has five layers, 8,192 hidden channels, 64 query heads, eight KV heads and head width 128. At TP8 the stacked matrix has shape 8,192 × 1,280 per rank. [Official draft model card](https://huggingface.co/RadixArk/Muse-Spark-Open-DFlash2/blob/main/README.md) · [V104 measured-parent analysis](../v104_v64_direct_draft_kv/README.md)

V73 shards the earlier 40,960-to-8,192 context projection. V108 moves that projection to the owning sequence-parallel rank during prefill, and V120b enables the correct registered Muse prompt path. V104 fuses five **decode** prefix-valid cache writes. V130 builds on V104, which uses scored V64 as its parent. It introduces bounded **prompt** materialization without new collectives or persistent model weights. ## Write path and cost

Each complete prompt slab calls the native draft FC over all input channels and native hidden RMSNorm, computes the ordinary stacked BF16 KV GEMM, and uses the existing V104 physical writer with a reused vector of full lengths. The width-eight groups in this call are solely a memory layout for the writer. Each input carries its original physical slot and absolute position, including where rows straddle a request boundary. A final one to seven rows go through the ordinary cache writer. All work completes on the original append stream before the scheduler can publish a reusable prefix. [Worker and host implementation](delta.diff)

| Per-rank allocation for 16,384 prompt rows | Native V64 | V130 aligned prompt |
| --- | ---: | ---: |
| One BF16 FC or normalized context result | 256 MiB | 64 MiB per slab |
| BF16 stacked projected K and V | 40 MiB in a retained workspace | 10 MiB temporary per slab |
| Two BF16 norm/RoPE staging buffers | 40 MiB in retained workspaces | Direct cache writes |
| Previously captured target taps | 1,280 MiB | 1,280 MiB |

The avoided intermediate stores and subsequent reads total **80 MiB per rank** over a full prompt chunk. These are logical tensor bytes. V64's full-size temporary and persistent allocations need not coincide at the process peak. Earlier fallback appends can already have grown its workspaces, and allocator reservation may outlive tensor destruction. V130 runs four FC, norm, stacked-GEMM and direct-scatter calls for a full chunk, and the dense FC weight is 640 MiB. Re-reading that weight and choosing a different GEMM shape can reduce speed or change last-bit BF16 results. The public V64 receipt reports +1.9 GB/GPU against the +2.0 GB limit and supplies no kernel timing. [V64 measured memory](../../runs/abd217baf0ed49fd.json)

The new flag defaults off. The frozen comparison uses V104's flags plus `--speculative-dflash-stream-prompt-kv`. Eligible prompts require the ordinary dense BF16 projector, unmodified FC and norm calls, and the verified native physical BF16 NHD pool. Torch compilation, CUDA capture, deterministic and batch-invariant modes, LiLiCorr, instrumentation and incompatible storage retain the native prompt path. Decode verification continues to use the pre-existing V104 flag. [Launch flags and source hashes](validation.json)
