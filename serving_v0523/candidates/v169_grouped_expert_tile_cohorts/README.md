# V169 narrower grouped expert tiles for cold prompts

V169 is strongest on partially filled prompt chunks. At 12,288 tokens in the uniform routing model it issues **18.9% fewer tensor-core row operations** than V168 with the same number of packed expert-weight tile reads. At a full 16,384-token chunk the modeled reduction is **1.8%**. Whether the reduction pays for measuring expert counts and sometimes issuing a second grouped launch needs an H200 comparison. The candidate carries V168’s five launch flags. [Official patch and rules checks](validation.json) · [Four-file delta from V168](delta.diff)

The published Humming 0.1.12 Hopper kernel uses a 176×256×64 thread-block tile for these two grouped projections. Every work tile performs the same-width matrix multiply, including the final partial tile of each expert. V169 precompiles two additional widths, 136 and 152. A local expert may use a narrower tile only when its exact route count requires the same number of tiles. The planner estimates the combinations of resident blocks for both projections and charges an additional full wave per projection when splitting the launch. It picks at most two widths per window. Every row retains full-K BF16 matrix multiplication with FP32 accumulators, the existing scaling and SiLU boundaries, and its original output token and weighted slot. [Pinned Humming release](https://pypi.org/project/humming-kernels/0.1.12/) · [Independent native schedule replay](independent_vendor.json)

The sparse-prompt exchange already transfers a small descriptor to the host. V169 replaces one rank-local route count with a histogram in that same transfer. Fixed histogram bins have integer centers. The feature restricts FP32 counts to exactly representable inputs. The per-rank histogram stays outside the common TP votes and collective decisions. Multiwindow, unsupported and failed-compilation paths retain the existing projections. A second cohort changes the integer sort keys in the existing stable sort and passes row slices of the original BF16 arenas to Humming. The per-expert scaling step sees the restored original expert IDs. At 32 local experts the extra host-bound payload is 124 bytes per layer. Histogram, sorting-key and index temporaries add GPU memory, and small cohort tables travel back to the device. Peak serving memory remains unmeasured. Each row includes 384 synthetic rank histograms. Each token chose eight different experts. The model uses 132 SMs, one resident CTA per SM and 989.5 dense BF16 TFLOP/s. The alternate widths never increase the number of complete packed-weight sweeps. Concentrating a quarter of route draws on rank zero forced its original bounded-multiwindow path in all 48 trials at each prompt length. The remaining ranks can still apply the planner independently, and time to the next collective depends on the slowest rank. [Model source](work_model.py) · [Full model results](work_model.json)

Historical H200 evidence measured 5.83 ms per layer for an earlier dense expert implementation and 6.62 ms for V40 Marlin at 16K. The scored Humming ancestor V64 reached 1.4119× overall. Neither measurement times these new grouped projections or reports the served distribution of window lengths and expert counts. Even the ideal elimination of all M padding previously modeled only 1.11× GEMM arithmetic at 16K. No end-to-end multiplier follows from the projected row savings. **Verification.** NVCC 12.9.86 compiled all six full production Humming source specializations for SM90a. All contain 32 static BF16 HGMMA sites of the requested width, use 168 registers per thread and retain the same 56 bytes of spill stores. The compiler reports 84 bytes of spill loads for each narrow specialization and 80 for its parent. Shared memory is 107,520, 115,712 and 128,000 bytes at widths 136, 152 and 176. The four additional cubins total 312,992 bytes on disk. Build successes and failures are cached per CUDA context and configuration. Startup latency and resident module memory still need measurement.
