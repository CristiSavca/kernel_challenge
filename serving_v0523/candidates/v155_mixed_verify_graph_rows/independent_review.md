# Independent review of V155 graph replay

On the native DFLASH target, V155 enters the prepared mixed layout through TP worker verification with FULL hidden capture. It carries an ordinary EXTEND body and asks its eager logits processor for the last row of each prompt and every raw verify row. The shared graph logits buffer accepts the new row count if it fits and falls back to eager output allocation otherwise. Breakable replay reconstructs the static forward batch on every call and carries that invocation's selector through the body into the eager head. Full graph replay uses a copy of the current user-facing batch for the head. The output trimmer keeps the requested P+W·T logits rows and the original count of real tap rows. The selector is outside captured CUDA code. TC-piecewise cannot replay this layout and takes eager fallback. [Official source and hashes](validation.json) · [Worker/typed metadata tests](worker_cpu.json)

The normal scheduler has no production call for this additional verifier argument on V155 alone. A caller still needs to build and safeguard the physical full/SWA slots for all tails, run the prefills and commits through the two native result consumers, and publish the next tail lengths. The archived H200 captured buckets show that simply adding every fitting tail increases combined padded-row work on 147 of 202 eligible high-load steps.
