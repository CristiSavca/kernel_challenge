# V194 shares full prompt chunks with running decode requests

V194 can move a few rows from an ongoing prompt chunk into its final partial chunk. The scheduler uses the space in the current target forward to verify the running requests’ real draft tokens. This gives mixed serving a path during the full 16,384-row prompt passes that previously consumed the entire graph. The scheduler admits the change only when the last prompt chunk still fits its original CUDA graph bucket. [Scheduler delta](delta.diff) · [Full official patch](patch.diff)

The budget uses the actual number of running requests times the captured verification width. Before the native chunk allocator runs, pure tensor-parallel ranks compare their proposals with a host all-reduce. A rank can veto because of capacity, request state, sampling or graph geometry. The underlying mixed path still checks the actual request identities and allocation before it shares the target forward. If that later check declines, normal serving can execute a shorter prompt chunk. Dynamic memory pressure and changes in competing work can affect the number of calls in a live schedule. In the archived V41 32-user run, 145 full prompt passes had running decoders. The log identifies the remaining prompt length reliably for four eligible continuations with 124 running-request appearances across them. At 16 users it identifies five partial continuations and none pass the final-bucket constraint. In a separate simulation holding 16 decoders ready throughout the archived 32-user cold prompts, 30 of 170 prompt forwards could also carry one group verification. Neither replay measures the savings, and the live rank vote has a cost. [Trace counts and assumptions](trace.json) · [Trace replay](trace.py)

The CPU harness ran 144 native chunk-adder cases, 20 additional rejection cases and asymmetric memory votes with real two-, four- and eight-process Gloo groups. A separate test followed 14,000 complete prompts with changing cohort counts and verification widths and forced 1,748 late vetoes. With fixed capacity it preserved every prompt row in order, the original prompt-forward count and the original padded-row budget throughout. The V160 fixture also ran on these sources for 96 admitted and 216 execution/fallback rounds. CUDA streams and model outputs in that fixture are simulated.
