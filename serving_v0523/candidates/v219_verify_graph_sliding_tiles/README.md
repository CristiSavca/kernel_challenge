# V219 sharded draft projection and sliding verification

V219 combines two changes to ordinary DFLASH target verification. During an eligible target graph replay, each tensor-parallel rank projects the complete input into its own draft output channels. The worker gathers the live projected rows once before applying the original normalization. In the same target pass, Hopper can read consecutive 64-row tiles directly from the physical sliding-window KV pool. Every attention boundary and irregular tile keeps its indexed loads. Both donor orders reconstruct the same serving tree. ## Work and memory

At TP8, the native draft projection has 40,960 inputs and 8,192 outputs. Each GPU computes 1,024 outputs over the full input width. Per-GPU FC weights needed for one eligible pass fall from **640 to 80 MiB**. The extra all-gather sends 1.75 MiB per rank at 16 users and an eight-row verify under conventional ring accounting. The code reaches consensus during capture and uses zero per-step CPU votes. V120b already implements output-channel sharding in a separate serving lineage. V219 brings it into V215’s ordinary target graph and retains raw features for fallbacks. [Projection geometry and capture sizes](../v217_captured_verify_context/geometry.json)

The new projection retains one 80 MiB immutable weight shard, one 20 MiB raw feature workspace and 4.5 MiB of local graph outputs across the 20 recorded shapes. Those objects total 104.5 MiB per GPU. Replacing distinct V215 output allocations would save 75.5 MiB overall. The actual change depends on graph-pool reuse. V64’s official run measured 1.9 GB over stock against the 2 GB limit, making peak memory an important judge measurement. [Allocation model](../v217_captured_verify_context/geometry.json) · [V64 result](../../runs/abd217baf0ed49fd.json)

For the 32-user later-turn trace, the sliding tile path covered 92.33% of logical KV bytes with the fresh simulated allocator and 1.96% after shuffling 64-row runs. Captured request lengths are real. The replay supplies physical slot order. The compiler emitted bulk loads for the eligible paths across all four served load shapes. [Allocator replay](../v218_sliding_verify_tile_transport/independent_geometry.md) · [Hopper compilation](../v218_sliding_verify_tile_transport/sm90.json)

The sharded path assumes published model weights remain immutable between supported loader updates. Those updates retire the frozen FC shard before writing. An out-of-band write through PyTorch’s `.data` can bypass the version counter and leave a stale shard. ## Connected checks

A 2,048-word BF16 sample from the V218 sliding attention interpreter drove the integrated candidate’s graph and draft projection tests. Four- and eight-rank Gloo runs compared 215,040 BF16 output elements, including rank-local weight changes, hooks and allocation failures. A separate CPU invocation used the full 8,192 × 40,960 weight matrix with eight verification rows. Its 65,536 projected elements and all 65,536 normalized elements matched the complete FC, bit for bit. GPU execution and live model weights were outside these tests.
