# V158 native DFLASH proposal reuse

V158 lets a coordinator draft for an already running request cohort once, then choose between combined prompt verification and ordinary standalone verification. If the mixed path declines, the original standalone verifier can consume the same proposal without executing the draft model again. The normal DFLASH worker uses these same functions for every nonempty decoding step. This change alone provides no measured serving speedup. [Official patch](patch.diff) · [V147 delta](delta.diff) · [Source identities](validation.json)

Call `propose_decode_block(batch)` on the native forward stream after reservation and resolution of the pending bonuses and committed prefix. The result contains the real [requests, native width] draft token IDs, absolute positions, allocator-global reserved slots, the target KV translation plan, and any sampled selector candidate IDs and their matching probabilities. `prefix_lens` is the authoritative device length tensor. `prefix_lens_cpu` retains the input batch's committed host mirror when available. A caller needing exact host lengths must resolve that mirror before invoking the API. The allocator reservation bound is a distinct quantity. No new synchronization or token allocation is performed by the interface.

The result borrows buffers for one serialized worker step. `is_current_decode_proposal(batch, proposal)` checks the worker-issued token, originating batch, current draft input, row owners, lengths and sample tuple without device reads. A second proposal invalidates the first before the worker touches shared buffers. A coordinator should call `consume_decode_proposal(batch, proposal)` exactly once after collective agreement to enter mixed verification. If it declines, `verify_proposed_decode_block(batch, proposal, on_publish=..., grammar_barrier=...)` takes that claim itself, verifies all candidate positions, publishes commit lengths and executes the original prefix-valid draft KV write. Only an opaque token is retained on the worker for ownership tracking.

The complete 334-line native proposal computation is byte-identical to its V147 parent. The regression fixture executes the original and extracted methods with CPU model/device stand-ins. In 216 combinations, both the normal public worker and the standalone-propose-then-verify path reproduced the original target inputs, publish and KV writes, outputs and call order. The cases include folded and eager selectors, two sampled proposal modes, Domino, ordinary and compact caches, allocator-bound host fallbacks, grammar handling, Mamba updates and the idle-peer graph guard. A forced preparation failure restored the original host length and sum and invalidated the consumed proposal. These tests exercise worker orchestration and tensor ownership. They do not time CUDA replay or evaluate model weights on H200. [Differential fixture](proposal_cpu.py) · [CPU receipt](proposal_cpu.json)

The 120,805-byte export contains one changed file relative to V147 and preserves its four flags. Full and incremental patches passed strict forward and reverse application. The V155 target readout and V158 proposal deltas compose in either order. Combined scheduling and its running-request admission, latency, accuracy and peak-memory effects remain separate integration and hardware work.
