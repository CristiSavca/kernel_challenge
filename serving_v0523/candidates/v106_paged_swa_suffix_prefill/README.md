# V106 paged sliding-window prefill

V106 combines V100c’s 160-token paged FA3 full attention with dense FA3 for long sliding-window prefills. The 16 full target layers keep the paged operator and its Hopper tensor-memory-load eligibility. The 46 sliding-window layers can use the dense operator after copying just the tokens visible to the query chunk. Both operators keep FP8 cache values, query and key positions, causal window, softcap, descales and output dtype. End-to-end speed and judge agreement remain unmeasured. The complete eight launch flags match the parent. [Exact flags and reconstruction](validation.json) · [Matched parent](../v100c_v64_paged_prefill_control/README.md)

For K cached tokens, Q query rows and inclusive left window L, the copied interval starts at max(0, K−Q−L). For each visible logical token t, the kernel uses the translated physical page from column floor(t/P), then adds the slot offset t mod P. K and V carry independent page and slot pitches. Source loads are predicated at token granularity, including the two partial pages. Page size is a compile-time constant. Fragmented cache pages, non-power-of-two sizes, unaligned byte payloads and disjoint graph padding are covered. Wide hybrid pools require a precomputed sliding-window page table. [Addressing and numerical oracle](independent_paged_oracle.json)

At two 64-wide FP8 KV heads, a full 16,320-token chunk with 2,047 visible prior tokens copies up to 4.48 MiB of payload per rank per sliding layer. That adds about 413 MiB of source reads and destination writes over 46 layers, before guards. At 32 request slots and a 16,384-token query capacity the two packed allocations use 22.05 MiB. The packer’s 48 MiB cap limits those allocations. Realized speed depends on whether dense FA3’s attention reads save more time than packing costs. Peak process memory, TTFT and the complete serving score require a hardware comparison. [Attention traffic review](independent_review.md)
