# V121 target vocabulary head feasibility

On the scored V64 architecture, ordinary greedy DFLASH verification already sends only each rank’s `(score, token ID)` winner per target row. The dense **local** FP32 matrix still exists. At one user, eliminating its four logical accesses could remove 3.08 MiB per rank in front of a 394.625 MiB input weight sweep. At 32 users the corresponding figure is 98.66 MiB. With no GPU profile attributing substantial latency to these accesses, a custom target GEMM is a weak candidate for the one-user path and an unproven experiment at 32 users. No patch was armed or submitted. [Traffic calculation and CPU checks](head.json) · [V64 official result](../../runs/abd217baf0ed49fd.json)

## Verify dispatch

The scheduler builds the DFLASH worker before capturing the target decode graphs. The worker finds the single `MuseSpark1xLogitsProcessor` through the base class and enables deferred verify gathering. The registered omni decoder constructs this processor through its text base. Its `torch.mm` multiplies BF16 hidden states and the BF16 head weight with FP32 output. The ordinary logits pipeline then multiplies the FP32 shard by the model’s scale and returns the local shard on eligible target verification. The selector sets its sampling state only for non-greedy requests on the folded graph. The worker's unadjusted greedy path applies the FP32 softcap and resolves local winners in tiles of 4,096, then gathers just two FP32 values per rank and row. The CPU replay exercised ten native fallback conditions, including grammar, logprobs, sampling, penalties and per-token adjustments. [Dispatch fixture](head.py) · [Registered model and worker discovery](../v120b_native_muse_prompt/independent_processor_dispatch.json)

V91 parallelizes the seven softcap tile decisions, resolves ties by the lowest global vocabulary ID and performs one signed 64-bit MAX reduction per row. It also removes the second greedy decision synchronization for that group. V85a handles the draft’s different contract. It rounds the full per-token, per-vocabulary result to BF16, retains 16 candidates per row and gathers packed scores and IDs. Its V88 integration already sits on the measured V64 parent. The draft and target share read-only weight storage, but draft candidate IDs are necessary to start the target transformer. Target hidden states are therefore unavailable when the same request runs its draft head. A single combined GEMM for that request would violate the existing dependency. ## Local work per rank

The weight geometry is 25,256 vocabulary rows by 8,192 BF16 channels. The four logical FP32 accesses are the head store, scale read and write, and the softcap reduction read. They can hit cache. Raw tensor bytes are neither HBM traffic measurements nor step timings. A fused epilogue would still need to enumerate every vocabulary entry, perform the original scale and softcap, publish partial winners and make the TP decision.

| Concurrent requests | Target rows | Target GEMM (GFLOP) | Four matrix accesses (MiB) | Relative to one weight sweep | V64 gathered winner tensor |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 8 | 3.31 | 3.08 | 0.78% | 512 B |

| 16 | 128 | 52.97 | 49.33 | 12.5% | 8 KiB |

For a model that reads one weight bank and makes four uncached local matrix passes, an ideal epilogue that removes all matrix traffic changes that component's transfer time by factors of 1.008, 1.031, 1.125 and 1.250. Compute, cache residency, attainable bandwidth, pointwise latency and the rest of serving can change those ratios. The measured judge frontier does not supply a head timing. The dense active FP32 result itself is 0.77–24.66 MiB per rank. Avoid crediting a local epilogue with removal of the full-vocabulary graph buffer, which the process also exposes to prefill and other graph consumers. ## Numerical and graph requirements

A CPU counterexample uses only BF16-representable factors over all 8,192 channels. Two possible FP32 addition orders give 2⁻²⁴ and 2⁻²³. A second vocabulary row between them reverses the winning token after normal scaling and softcap. This proves that specifying FP32 accumulation alone cannot establish agreement with the native GEMM. A separate case shows why applying softcap after raw argmax can return the wrong ID when unequal raw scores saturate. The pairwise max with NaNs also changes winners under reassociation. V91 preserves the original reduction layout for that case. These are synthetic counterexamples, unrelated to the judge’s inputs. [Rounding, saturation, NaN and 1,296 finite tie cases](head.json)

The same target decode graph serves clean greedy and adjusted or non-greedy requests. The worker chooses the branch after replay and slices graph padding to the live requests. Capturing a compact greedy-only answer into that shared output would discard the logits needed on a later replay. A full-fidelity redesign could carry the final target hidden rows out of the graph, run the complete local head once for the applicable mode, and return the native scaled logits for every fallback. That adds an eager launch boundary and must preserve the original GEMM and all softcap tie behavior. Splitting one native GEMM into multiple smaller calls for vocabulary tiles also changes its algorithm choices and launch count. A matched H200 trace at 32 users that isolates the local GEMM, scaling, softcap, and collective would distinguish a slow GEMM from avoidable materialization. V88 isolates the draft change against V64. V91 isolates the target reduction against V89 and preserves the underlying target projection. V121 spent no GPU quota.

## Dispatch correction found during this audit

V108's startup prefill guard demanded the exact base `LogitsProcessor` class, so it rejected the registered Muse subclass even though native hidden capture and pruning are inherited. V111 and V120 inherited that guard. V97 uses a different helper. V120b accepts the native subclass, still rejects unknown processors, and preserves hook and override fallback. Independent execution reproduced the disabled path before the change and the active projected prompt path after it. This correction concerns prefill. The target greedy verification path described above was already active. [V120b constructor and guard regression](../v120b_native_muse_prompt/independent_processor_dispatch.py)
