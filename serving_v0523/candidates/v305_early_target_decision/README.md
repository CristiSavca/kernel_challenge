# Can a partial target head release the next DFLASH block?

A numeric softcapped logit can certify an early winner once it reaches the exact maximum representable capped score and every smaller token ID has been checked. V302 assigns contiguous, increasing vocabulary IDs to its eight ranks. When each rank advances by one local vocabulary page at a time, a still-needed row whose first saturated winner belongs to rank 1–7 requires rank 0 to scan to the end of its 25,256-token shard. A row with no saturation also requires that sweep in the absence of another certified bound. For this paging strategy to shorten the slowest rank's cold head read, every row still required for the decision must permit an earlier stop. A partial rival can prove a rejected suffix irrelevant while leaving the actual correction token unresolved. V131 already tests the rival and a weight-norm certificate. [Native decision replay](check.json) · [Earlier rival certificate](../v131_exact_verify_pruning/README.md)

We ran V302's actual cross-rank winner selection, greedy accept and commit functions on 1,024 engineered rows across all 128 proposal match patterns. Local PyTorch softcap and an in-process all-gather supplied the rank data. The partial-page certificate recovered every native decision. Two numerical controls presented identical visible pages but required different correction IDs. One had a smaller-ID saturated tie on an unread page, and the other had a higher unsaturated winner. The separate first-NaN mode gives a later NaN priority over a saturated numeric value and needs its own certificate. The constructed success frequency does not measure the model. The archived serving records contain no native scores or saturation-frequency measurements. [Cases and native source hashes](check.json)

## Preparing draft KV beside the head

V302's normal capture computes the local target-tap context projection after the target forward returns its logits. A different schedule could privately stage that 80 MiB projection and the five subsequent local KV projections, totaling another 20 MiB of BF16 weights, before the complete greedy result is available. They depend on target features and positions. The committed cache write still needs each request's accepted length. The replay ran the production stacked helper's BF16 GEMM, its five layer callbacks and native accept/commit. Deferring publication from a private copy reproduced 81,920 BF16 cache words. Releasing shared helper workspace before a later materialization overwrote 20,400 live words in the negative control. The norm/RoPE kernel and physical device writer were modeled. Public-width private K/V payload is 20 KiB per user per rank, up to 640 KiB at 32 users. Stream ordering, raw-tap lifetimes, communication and graph ownership remain necessary. [Executable worker and buffer replay](check.py) · [Captured context geometry](../v217_captured_verify_context/geometry.json)

The native target head reads 394.625 MiB of weights per rank. With first-touch BF16 weights and the same number of live input rows, the head, context FC and KV projections have the same leading arithmetic intensity of one FLOP per weight byte per input row. The sum of their separate H200 compute/bandwidth roofline times therefore equals the combined roofline time. Scheduling them simultaneously could hide underutilization and launch gaps, while the same tensor cores and HBM still perform their work. Using the measured shaped 64 MiB pooler as a linear weight-traffic proxy, one-user head cost is 0.156 ms and independent draft preparation is 0.040 ms. Even free overlap of those proxy times yields about **1.002× one-user streaming**, falling to 1.0006× at 32 users. Native TP gather latency and any real interval of GPU underutilization were not measured. The actual prior-node one-user period would need a 7.92 ms saving for 2×. A critical-path measurement of the head, FC, gather and five-layer materialization on the same warmed node could distinguish these cost assumptions.
