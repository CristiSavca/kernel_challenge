# Independent V141 route ownership review

The test executes the production per-expert planner and outer W13/W2 projection loops in C++ with a coroutine implementation of warp ballot. It samples lane and expert execution orders, provides dirty plan storage between replays, and checks the original production output row/channel expressions independently from the reference stable filter. Every valid local route must own every output column once. Repeated selections of one expert stay distinct slots. Empty or remote slots produce zero writes. The test includes 1–64 local experts, 1–2,048 slots, nonmultiples of 32, all routes at one expert and exact 8/16/32 boundaries.

The final header passed 850 cases and 765 dirty-buffer replays. It published 12,975 empty lists correctly and assigned 73,754,240 W13/W2 output coordinates exactly once. The original input row for W13 is the route slot divided by top-k. W2 consumes the activation for the original slot itself. All lanes participate in each ballot. Each expert owns its own count and at most S ids, so a hot expert can fill its entire S+1-int32 segment without writing into its neighbor. The release W13 advances in tiles of 16 rows, W2 in tiles of 32. At 32 local experts and 2,048 slots the plan occupies 256.125 KiB. This suite exercises planning and ownership. Numerical and CUDA code generation checks are recorded separately. [Source-level driver](independent_plan.py) · [CPU result](independent_plan.json)

For a synthetic distribution with eight distinct, uniformly chosen global experts per token, the count for an individual expert is binomial with probability 8/256. Conditional on an expert being active, the probability of more than eight rows is 0.019%, 1.985% or 40.756% at 512, 1,024 or 2,048 global slots. The probability of more than 16 at 2,048 slots is 0.317%. Thus one rank has about 0.62 experts above eight rows at 1,024 slots and 13.04 at 2,048. Reusing a bank across multiple eight-row fragments primarily affects the largest of these shapes, unless the real router is more concentrated. The actual V139 comparator uses indexed Humming with its own tile reuse. Any speedup also depends on vendor kernel efficiency, removed packing/activation work, cache residency and the uneven work assigned to hot experts. The synthetic counts establish no H200 speedup.
