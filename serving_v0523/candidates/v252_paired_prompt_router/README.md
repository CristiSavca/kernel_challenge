# V252 shares the input tile between the router's two BF16 matrix products

V68 represents each FP32 router weight as a high and low BF16 factor. V252 retains both factors, accumulates both full-width matrix products separately in FP32 and adds them after the K loop. A single Hopper launch reads one activation tile for both factors and stores the final FP32 logits. The prefill entry, tensor-parallel ownership, routing sigmoid, bias, top-eight selection and expert computation follow V68. On a 16,384-token TP8 chunk, each rank owns 2,048 rows and launches 256 thread blocks. The native two-GEMM path handles underfilled grids and unsupported tensors, devices, compilation and deterministic settings. [Patch](patch.diff) · [Public-contract validation](validation.json)

All eight compile cases emitted BF16-input, FP32-accumulating Hopper warp-group matrix instructions with zero spill bytes. The production tile uses 64 registers per thread and 49,152 bytes of shared memory. The CPU Triton interpreter matched 561,408 FP32 logits and 19,040 selected expert IDs against a blocked reference across seven fixtures. Five separate MoE entry tests also exercised the actual outer dispatch, including the native fallback. [Compiler](sm90a.json) · [Kernel checks](kernel_replay.json) · [Integrated dispatch](independent_router.json)

**Qualification is open.** A cancellation fixture found 68 of 256 cases where two valid FP32 reduction orders differ. One such result crosses the eighth-expert boundary. The before/after GPU libraries can choose different K-reduction orders, even with both BF16 factors and FP32 accumulators. The host fixtures establish neither a real H200 discrepancy nor stock-equivalent generated tokens. Keep V252 experimental until a physical comparison establishes agreement and throughput. The logical copy and traffic model for this stage corresponds to roughly 0.03% of historical end-to-end time at nominal bandwidth.
