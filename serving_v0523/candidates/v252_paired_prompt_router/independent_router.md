# V252 router dispatch, arithmetic and reach

The official V252 tree `f756a14800e6919cb945898cb1709283333d39a5` reached the paired kernel from the original Muse MoE owner-row entry. The V68 fixture separately observed the same owner rows with real TP2/4/8 Gloo collectives. On TP8, 16,384 prompt rows give 2,048 owner rows. The measured configuration uses 256 experts and the H200 has 132 SMs. The launch grid is 32 × 8 = 256 CTAs. Exactly 1,024 owner rows produce 128 CTAs and run V68's two original GEMMs. A 1,025-row shard produces 136 CTAs and can enter V252. The V41 hardware archive records disabled Torch compilation. The public V68 check passed at 17,512.9 tokens/s/GPU at 16 users. The five host cases used the submitted gate, its native factor preparation, and the pinned reference for sigmoid, biased top-eight selection, normalization and packed output. They exercised a finite narrow tie, unsupported K, the SM-wave cutoff and the 2,048 × 8,192 × 256 production shape. Three calls selected the new launcher and two selected both original matrix multiplications. The checked CPU model also executed 300 actual Triton program bodies. Four complete CTAs at the full shape covered the opposing row and column boundaries. The full-size host launch used CPU GEMM for its result. [Source-bound results](independent_router.json)

**FP32 reduction order can change the eighth expert.** In 256 adversarial finite BF16 dot products, the CPU BLAS result differed from a CPU execution of the submitted K64 accumulation structure in 68 cases. One logit used products `2^24, 1, -2^24` at indices `72, 114, 6`. BLAS returned 1 and the block model returned 0. With a competitor at 0.5, the pinned top-eight operator selected expert 7 and expert 8 respectively. This is a real host numerical difference. H200 cuBLAS and HGMMA may perform different internal additions from either CPU implementation, and checkpoint traces do not establish how often similar close margins occur. Physical token agreement remains open. [Counterexample and logits](independent_router.json)

At 2,048 owner rows, both designs perform 17.18 GFLOP per sparse layer. Under a one-sweep logical byte model, sharing the input saves 32 MiB and avoiding the FP32 intermediate/add saves another 8 MiB per rank. The resulting 40 MiB corresponds to 8.74 µs at 4.8 TB/s. Register reuse, L2, tile rereads, kernel launch latency and concurrency with the native pooler determine actual elapsed time. The V41 trace includes 75 full prompt calls at 16 users and 150 at 32. Applied across 62 layers, that byte conversion amounts to 0.041 s and 0.081 s, respectively, approximately 0.025–0.027% of the observed wall times. Achieving 5% higher whole-trace throughput from these same calls would require a net 1.688 ms and 1.559 ms per router layer. The H200 standalone projector archive stops at 256 rows, and there is no measured V252 comparison at the critical 2,048-row shape.
