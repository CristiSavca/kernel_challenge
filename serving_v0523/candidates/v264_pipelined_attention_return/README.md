V264 splits the Muse attention output weights into two contiguous output-channel slices. Both GEMMs consume every local attention head for every prompt row. As soon as the first half of the channels is ready, a second stream starts its native reduction and copies this rank’s token rows into the output. The next GEMM can then run alongside the first reduction. Its result supplies the remaining channels. The returned tensor is compact and has the same row order, width and zero padding as the existing sequence-parallel path. [Change from V256](delta.diff) · [Full export](patch.diff)

At 16,384 tokens and TP8, the original 16,384 × 1,024 by 1,024 × 8,192 GEMM becomes two GEMMs with 4,096 output channels. Each GPU performs 274.88 billion operations and still owns a 16 MiB weight matrix. The original 256 MiB reduction becomes two 128 MiB reductions. Total logical collective payload stays the same. Splitting can introduce another 32 MiB input read and 64 MiB of logical traffic for copying the owned output. For in-place NVLS all-reduce the named projection and output buffers rise from 256 to 288 MiB. An out-of-place reduction with a full-size result would use 512 MiB under the parent and up to 416 MiB in the striped stages. These figures exclude allocator reuse, graph residency and backend workspaces. V150 uses direct peer sends and its own FP32 summation kernel. V264 uses the SGLang group’s reduction. - The constructor takes a CPU-group MIN vote on Hopper, compatible rank order, dense frozen BF16 weights, deterministic settings and LoRA. Each stripe must contain at least 64 MiB for the native width in this experiment. The full projection and both real contiguous stripe buffers must pass identical SGLang dispatch checks before either collective can start. ## Exposure to the 4× objective

On the archived V41 prefill schedule, 75 calls at 16 users and 150 at 32 users had enough real tokens to enable this geometry. At 989 TFLOP/s dense BF16 and an illustrative 450 GB/s per direction for a ring collective, perfect overlap would save 0.646 of 164.83 seconds at 16 users and 1.291 of 304.43 seconds at 32. At 400 TFLOP/s and 225 GB/s those values rise to 1.598 and 3.193 seconds. Actual throughput depends on the relative speed of the stripes, scheduling and contention with the reduction. H200 memory peak, TTFT and throughput remain unmeasured. V64 holds the verified four-load score of 1.4119×.
