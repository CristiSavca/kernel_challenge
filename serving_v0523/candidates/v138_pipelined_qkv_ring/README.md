# V138 overlaps the QKV projection with token exchange

On V64, each eligible Hopper sequence-parallel prompt layer first gathers all token rows to every tensor-parallel rank and then launches its dense QKV projection. V138 projects the locally owned shard immediately. A second CUDA stream forwards this shard to the next rank while receiving a different shard from its predecessor. Every rank projects every shard once against its own BF16 weights. Outputs go directly to their original rank-major row ranges. The final SP narrow removes alignment rows. This competes with V113, which exchanges weights and projected head rows between rank pairs. [Candidate](patch.diff) · [Three changed files relative to V64](delta.diff)

At 16,384 rows with 8 ranks, 8,192 hidden channels and 2,304 QKV channels per rank, the receive buffers occupy 64 MiB against 256 MiB for V64’s gathered tensor. Including the output and a temporary projection result, the named allocations fall from 328 to 145 MiB per rank per layer. Each rank still sends 224 MiB in the ring and performs the same 618.48 billion dense floating-point operations. Eight smaller GEMMs and seven additional logical reads of the 36 MiB weight can offset the gain if tensor-core efficiency or overlap is poor. The figures describe individual operations, not process peak GPU memory or throughput. [Geometry](geometry.json)

The model enables the ring on the Hopper replicated-expert SP route after a collective startup vote checks that every rank has a PyNCCL communicator, compatible rank ordering, and unquantized frozen BF16 QKV weights. The ring uses the same configured BF16 dense backend. Changing GEMM row counts may change the vendor kernel's accumulation order. Dispatch retains the ordinary gather for short shards or wide heads, with no reference to request identity or concurrency. Each receive waits for earlier reads of its reused buffer. The next GEMM waits for its own receive. All transfer work joins the caller stream before the custom op returns. [Implementation](delta.diff)

The regression executed the installed CPU PyTorch custom-op dispatcher and the actual patched column entry with 4 and 8 real Gloo ranks. Seventy-two rank cases tested output ordering, ragged tails, strided shards, disabled paths, rank agreement and backend selection. An independent two-stream access model checked conflicting reads and writes in the ring. The full-K host fixture tested 29,952 BF16 results. The official CLI exported the patch, and both forward and reverse application matched the recorded trees. The candidate awaits NCCL/CUDA graph replay, output agreement, TTFT, peak memory and throughput on the official H200 node. [CPU results](cpu_result.json) · [Export and flags](validation.json)
