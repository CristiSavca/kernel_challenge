# V217 captures the draft context projection during ordinary verification

V217 runs one eighth of the 40,960-by-8,192 draft context FC on each target tensor-parallel rank during CUDA graph capture and replay. Each GPU reads an 80 MiB BF16 output-channel shard. V215’s ordinary verifier reads all 640 MiB and computes the complete output on every rank. At 32 users and width eight the work falls from 171.80 to 21.47 GFLOP per rank per pass. V120b previously partitioned these same output channels in an eager post-verify worker. V217 brings the native full-K projection into the target graph and changes how the graph stores the five raw captures. **V217 has no H200 throughput, output-agreement, TTFT, or peak-memory result.** [V215](../v215_decode_reduction_paired_context/README.md) · [V120b](../v120b_native_muse_prompt/README.md) · [Geometry](geometry.json) · [Official export](patch.diff)

## Capture and replay

Each of the five native target taps casts the current residual stream directly into its slice of a shared raw BF16 buffer. The target graph's tail projects that buffer through its immutable shard of the draft FC. It preserves the original raw features. Replay slices both tensors to the actual token count. During the ordinary worker’s accepted-prefix append, all ranks gather their live BF16 projection columns in channel order and apply the draft’s original full-width RMSNorm. The worker passes the same accepted lengths, physical slots and positions to its existing KV writers. At 16 users each rank receives 1.75 MiB of peer projection data. V217 adds one device all-gather and zero host votes per eligible pass. [Seven-file delta](delta.diff) · [Real model and logits entry](independent_model_entry.md)

The full target decode backend allocates the raw workspace before recording the graphs. The eight-rank V68 log records 20 batch sizes, with a maximum of 32 and a sum of 288. If V215’s per-shape raw output objects each occupy their own storage, their payload totals 180 MiB per rank. V217’s shared raw workspace occupies 20 MiB, the private weights occupy 80 MiB and the per-shape projected outputs total 4.5 MiB. That gives 104.5 MiB of retained tensor payload, a modeled saving of 75.5 MiB per rank. Peak allocator memory can differ from that sum. Before crediting any released parent storage, the added persistent payload is 104.5 MiB, and the largest live gathered output is another 4 MiB. V64 reported 1.9 GB over stock against a 2 GB cap. V68 reported 1.7 GB at 16 users. ## Correctness and supported configurations

The target graph runner requires the native Muse body, plain dense BF16 draft FC, full decode CUDA graphs, Hopper, the existing sequence-parallel draft-context flag and a shared target/draft TP group. The direct writer requires unique configured taps. Graph capture checks for target instrumentation, multi-stream multiplexing, two-batch overlap, ragged verification and compilation. A CPU rank vote after each captured shape enables its shard only if every rank returned the exact raw workspace. Other callers can retain their ordinary raw hidden states through eager execution. A rank-local allocation failure releases newly attempted workspace and weights on every rank. An existing earlier capture keeps its storage. [Production guards and worker entry](delta.diff) · [Failure fixtures](replay.py)

On every eligible replay, the worker gathers private weight-snapshot results before checking local FC hooks, replaced or mutated parameters, or supported loader invalidation. An affected rank recomputes its own native projection from the live raw taps. Other ranks receive their clean original output channels. Supported draft disk, tensor, distributed, IPC and external transfer updates invalidate before mutation, including loads that fail partway. This covers ordinary and inference-mode parameters. Direct unannounced writes through the PyTorch `.data` escape hatch bypass tensor versioning and supported loader callbacks. ## Evidence and limits

Real four- and eight-rank CPU Gloo runs compared 837,120 BF16 target-tap elements and 215,040 normalized output elements by bit pattern. They cover seven padded/live capture pairs, immutable peers after rank-local hooks and source mutations, supported inference-parameter edits, rank-asymmetric capture mismatches, three allocation-failure scenarios and recovery. One trajectory consumed all 2,048 BF16 words emitted by the V218 sliding-attention interpreter. The replay accepts that JSON as an optional second argument after the patched SGLang tree. An independent test exercised the actual outer Muse model, inner decoder and pinned logits processor. [Replay and timings](replay.json) · [Runner](replay.py) · [V218 witness](../v218_sliding_verify_tile_transport/interpreter.json) · [Independent model coverage](independent_model_entry.json)

The rejected per-step CPU-vote design took about 231 µs at four processes and 330 µs at eight in this host-only Gloo run. V217 only votes while setting up captures. At the published H200 peak of 4.8 TB/s, the 560 MiB reduction in a cold FC read corresponds to 122 µs. Actual cache hit rates, native GEMM algorithms and communication determine the exposed time. H200 evaluation must establish numerical agreement after the GEMM shape changes and whether the overall serving score improves. The full and relative patches apply and reverse on public commit `297e54fd`, and the six launch flags are inherited from V215. V64’s official four-load score remains 1.4119×.
