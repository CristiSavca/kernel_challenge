# V254 adds native split router logits during expert selection

Both router projections use V68's original BF16 input and factors, column layout, two separate `torch.mm(..., out_dtype=torch.float32)` calls and FP32 outputs. The existing CUDA router loads both outputs and adds the two FP32 values with an explicit round-to-nearest instruction before the original multiplier, sigmoid or softmax, bias, stable top-k, score normalization and optional packing. The two original dot-product reductions keep their order, including on nearly tied experts. [V68 delta](delta.diff) · [Official full export](patch.diff) · [Rules and round-trip verification](validation.json)

V68's Humming replicated sequence-parallel prompt path gathers the owner-local expert input, scores and IDs. It has no downstream full-logits consumer. Non-SP Humming also uses only the route outputs. Nonreplicated SP receives the original completed logits tensor for its dispatcher. The public `forward_split2` continues to return a single summed FP32 tensor. Hooked, traced, alternative-provider, compile and deterministic paths keep the normal materialized call. A build error on the optional CUDA module declines before either GEMM and is cached by kernel geometry. Hot-path allocations stay on the router side stream. Both GEMM outputs already coexist at V68's add; V254 keeps them until the immediately following router load. This can overlap their lifetime with routing output buffers. At M=2,048, these three eight-column outputs occupy 192 KiB/rank. [Normal-call differential replay](dispatch.json) · [Source](check_dispatch.py)

At one request and width 8, V68's original split projection is inactive. At a full-prompt owner shape, 4 MiB corresponds to 0.87 µs at 4.8 TB/s HBM bandwidth. The 75 and 150 long-prompt calls in the archived 16- and 32-user V41 traces put this traffic conversion at roughly 4 and 8 ms across 62 layers. Launch latency, cache residency, stream overlap, shorter prompt calls and non-SP verification can produce different wall-time effects. The measured V68 parent reached 17,512.9 tokens/s/GPU at 16 users. V254 has no physical measurement. The CPU host replay exercised the actual old and new model methods, route selection, JIT bindings, SP consumer, non-SP return, backward/forward hooks, Torch function and dispatch modes and the full production shape. Each of 25 paired calls issued two same-shaped, same-stride CPU GEMMs over the BF16 operands. All 739,328 summed logits and 23,104 selected expert IDs matched; score, packed ID, instrumented logits and synthetic expert returns also matched. A separate CPU C++ replay executed both submitted CUDA warp bodies, with equal host substitutes for CUDA warp intrinsics and approximate exponent/divide. It covered mapped, padded, tied and subnormal values under sigmoid and softmax in 48 cases. [Host replay](dispatch.json) · [Warp replay](warp.json)

All 12 TVM-FFI wrappers compiled to Hopper SM90a machine code with CUDA 12.9, covering V68, V254's materialized entry and its split entry at one/four warps with PDL on/off. All used 43 registers and zero spill bytes. Each split case added two vector loads and eight `add.rn.f32` operations for eight FP32 values per lane. The normal routing arithmetic and padded-row behavior come from the same C++ body. The build and local tests establish static code generation and controlled numerical equivalence.
