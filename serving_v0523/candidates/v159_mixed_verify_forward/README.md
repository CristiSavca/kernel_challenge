# V159 mixed DFLASH target forward

V159 connects a native speculative proposal to one prompt-and-verification target pass. It combines V156's target and settlement, V157's graph admission, and V158's single-use proposal ownership. The entry point requires a prepared, reserved prompt batch and a resolved decode batch. It owns no scheduler entry. Physical H200 throughput and memory remain unmeasured. The official export is 172,923 bytes with SHA-256 `19b54bc3d3618ec7cfe699c8ca65698918d46d7ef2aacffbe04b3ff2ff12c229`. [Official patch](patch.diff) · [Connector changes](connector.diff) · [Manifest and parent hashes](validation.json)

The worker keeps the original batches intact. It uses the proposal's actual token IDs, absolute positions and allocator-global slots to build a causal EXTEND view. The model's KV translator resolves those slots for the target and the draft. Each rank checks its captured prompt, verify and combined graph keys. One CPU TP collective compares their padded sizes, the exact raw request and token counts, and a digest of the ordered request IDs, pool rows, lengths and prefixes. A decline leaves the proposal available for V158's ordinary verifier. On agreement the bridge claims the proposal, waits for the native HiCache consumer and invokes the target once. V156 then samples the prompt, accepts the native tail chain, writes draft KV for the accepted rows and publishes a single length tensor.

FA3 can publish committed sequence lengths only on the GPU. A plausible mixed round with no exact host mirror copies one 64-bit length per decoding request to the CPU after the cheap geometry and state checks. This transfer can wait for preceding GPU work on the same stream. Entering the combined branch also requires host consensus and construction of three metadata views. Those costs limit the gain from avoiding a separate target pass. In the saved V41 capture geometry, V157 admitted 66 of 112 opportunities at four users, 99 of 238 at 16, and 55 of 347 at 32. These historical counts do not establish a V159 speedup. [Historical graph geometry](../v157_mixed_graph_admission/cpu_result.json)

The CPU fixture completed 96 accepted joins, with all possible commit lengths from one through eight and 48 GPU-only length cases emulated on CPU. Each accepted join executed one target through the real EXTEND metadata, graph adapter, prompt sampler, chain accept and host packaging methods. Cases included FULL and Breakable body replay, synthesized expert outputs and native BF16 draft-store orchestration. Six rejection cases checked preserved ownership and no target execution. Six further runs executed V158's actual proposal and standalone verification methods after a decline and matched the regular worker's outputs. Real CPU Gloo collectives tested TP groups of 2, 4 and 8 under agreement, rank refusal, cohort disagreement and graph-size disagreement. [Reproducible tests](bridge_cpu.py) · [Results](bridge_cpu.json)

Call `try_forward_proposed_mixed(worker, prompt_batch, decode_batch, proposal, on_publish=...)` at the same point on every TP rank after proposal generation. A result carries both role outputs. A return value of None leaves the proposal with the caller, which can pass it to `worker.verify_proposed_decode_block(decode_batch, proposal, ...)` before the next proposal. V159 is an integration component. Its serving submission has the four inherited V64 flags and does not enable an admission policy on its own.
