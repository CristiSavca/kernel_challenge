# V176 compatibility and resource audit

The V176 patch has SHA-256 `08e5e126fe79b5fb37e706a8cbf8c8fdc449ef6794500200928f350462c44eb6`. All 825 added or removed source lines from V169, V171, V172 and V174 are represented relative to V168. The only extra signed line is empty. During review we moved the runtime-only verification schedule to the end of the ForwardBatch field list. That retained the original meaning of 40 trailing positional arguments. The final public signatures preserve all 131 ForwardBatch and 24 LogitsProcessorOutput positions. All 80 direct calls to ForwardBatch in the pinned source and tests use keyword arguments. [Executable audit](independent_registration.py) · [Full results](independent_registration.json)

**Launch compatibility.** The pinned CLI helper and msgspec 0.22.0 parsed 32 combinations and orderings of the recorded launch flags. The optional sparse exchange, prompt projection and verification schedule switches each default to false. The final ordering preserves all 546 positional ServerArgs fields from the pinned release. Eighty invocations of the model’s native configuration hook used simulated platform and topology capabilities. The Hopper TP4/EP4 and TP8/EP8 launch configurations passed. The feature-off path retained ordinary initialization across all five tested platform classes. CPU, ROCm, other NVIDIA generations, pipeline or context parallelism, attention DP, mixed chunk, and deterministic collectives were rejected when the enhanced Muse W4A16 LayerNorm SP setup requested them.

**Phase interactions.** V169’s tile choice occurs locally after sparse prompt routing has agreed on ownership. Its optional Humming compilation and per-rank tile choice change neither the all-to-all splits nor the return buffer indexing. V171’s full-K projection and Gloo eligibility vote occur at the end of prompt processing. V172 scopes schedule tensors to a single target verification and restores the previous field in a finally block. V174 consumes the same original routed-slot IDs as V168’s decode branch. Its registered-device checks preserve the existing medium kernel fallback when tensor maps or alignment are unavailable. Prompt and verification tensors can still live together in allocator or captured graph pools.

**Resource limit.** The official V64 scored result reports 1.9 GB over stock against a 2.0 GB limit. This leaves roughly 0.1 GB using the rounded reported values. At native width eight and top-eight routing, V176’s BF16 routed activation and output arrays are 16 MiB at 16 users and 32 MiB at 32 users, plus 131,200 or 262,272 bytes of INT32 plan storage per active layer. V173 already allocated these arrays. V174’s actual SM90a kernels compiled with 53 registers and 45,600 bytes of shared memory for gate/up, and 55 registers and 35,872 bytes for down. Neither spilled. The four optional narrow Humming cubins occupy 312,992 bytes on disk. Their per-CTA shared requirement ranges from 107,520 to 115,712 bytes, below the existing 128,000-byte prompt specialization. Decoding and prompt GEMMs run in different phases. On-device module residency, the graph allocator’s peak, startup time and total serving memory remain unmeasured on V176.
