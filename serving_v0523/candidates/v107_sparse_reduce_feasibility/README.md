# Sparse target verification and the expert all-reduce

**Decision. Retain the current expert reduction.** A fused Humming finalizer and one-shot push on H200 could remove one launch per active MoE layer at eight target rows. The proposed fusion still needs each rank’s complete 4,096-feature weighted expert sum before the unpool projection. It saves just 7.75 MiB of local BF16 write/read traffic across 62 layers. W13 and W2 together read about 12 GiB per rank and pass under the earlier uniform cold-bank model. Other rank distributions may change bank traffic, but they do not remove the dense projection’s dependence on every feature. [Traffic audit](../../runs/low_load_expert_traffic_feasibility.md) · [Executable calculations](check.json)

The exact pinned SM90/TP8 selector uses one-shot push only through 128 KiB. At eight verify rows both the 64 KiB expert output and 128 KiB attention output qualify. At 32 rows the 256 KiB expert result selects two-shot pull and the 512 KiB attention result selects multicast two-shot pull. V71 already gives the latter a direct producer workspace. V75 and its descendants already shard the unpool output columns and defer their gather to the fused FFN residual/norm boundary when eligible. Each rank still requires every input feature to compute its own output columns. [Native selector](../../sglang/python/sglang/srt/distributed/device_communicators/configs/custom_all_reduce_v2.py) · [V71](../v71_direct_multicast_workspace/README.md) · [V75](../v75_sharded_decode_projections/README.md)

Moving the unpool before the BF16 sum changes valid results. With rank partials (1,1) and (1,256) and unpool weight (1,−1), the original order yields −254. Projecting first gives −255. Moving the per-route RMS after the contribution sum or absorbing the W2 scale into RMS also changes outputs in the executable tests. The generic native fused MoE all-reduce normalizes after the sum when requested. The Muse-specific fused finalize expects TRTLLM output and its setup only enables Blackwell. A Hopper port would need the Humming route-to-row and scale-ID maps, original BF16 global-scale multiplication boundary, full per-route RMS, original slot order, rank reduction and graph-safe shared counter advancement. [Numerical checks](check.py) · [Generic fused operator](../../sglang/python/sglang/kernels/ops/communication/all_reduce_fusion.py)

Keeping the exact arithmetic but distributing complete tokens would first reduce each token to one rank. That rank must fetch the whole 64 MiB unpool matrix instead of its 8 MiB output shard. Dividing ranks into two, four or eight token groups adds 8, 24 or 56 MiB of cold unpool weights per rank per layer. Local caching or custom communication could change the achieved time. A one-shot optimization still needs 27.125 MiB of logical peer payload per one-user pass, before any multicast implementation benefit. Sparsifying rank participation under uniform top-8 routing seats an average of 5.295 of eight ranks per row. [Geometry](check.json)

V64 reported 4.0 mean committed rows and 203.2 median decode tokens/s per user at concurrency one. Their quotient gives an illustrative 19.7 ms per pass. Doubling or quadrupling that decode rate with a single saved boundary per MoE layer would require about 159 or 238 microseconds saved at each layer. Those are sensitivity calculations using separate aggregate measurements. The available serving receipt contains no phase timing supporting that scale. The end-to-end challenge score also includes the other loads. There is no production export or judge submission from this audit. [Official V64 result](../../runs/abd217baf0ed49fd.json)
