# V255 private draft window metadata

V255 extends V253 on the pinned serving checkout. Its two-file delta bounds page-table construction for the five-layer sliding-window DFlash draft. On the public model, an eight-token bidirectional draft with a 2,047-token radius needs at most 2,182 key addresses per request. The metadata kernel starts at the preceding 128-key FA4 tile and looks up both the virtual slot and its current physical SWA slot. Global query positions, source IDs for writes and the model’s original layer window remain intact. The graph path continues to reserve the original full-width tables for idle, custom or generally translated layouts. Its backing allocations and the roughly 48 MiB of additional static graph tables previously identified for TP-local batch 32 and 131K context remain. Eligible eager calls allocate two bounded tables. At the maximum public batch those use 558,592 bytes together. The policy requires native SM90 FA4, fixed-width private page-one BF16 storage, normal per-layer calls and local bidirectional attention across every draft layer. It takes the largest layer radius. Hooks, overrides, custom masks, ragged queries and unsupported layout states retain native handling.

In the archived V41 eight-H200 trace the first observed draft block of each request at concurrency 16 contained 17,237,738 logical key columns across 208 requests. Applying this rule leaves 441,578. At concurrency 32 the corresponding count falls from 34,363,904 to 881,920 across 416 requests. At public context capacity, the two-plane metadata launch shrinks from 1,025 to 18 column programs per row. This changes address construction once per draft call. It does not remove five independent attention computations or establish a whole-service speedup. [Trace inputs and shape counts](../v188_draft_window_metadata/independent_geometry.json)

Its interpreter reproduced 1,258,552 physical IDs across 96 launches and checked 8,687,440 padding columns. The candidate has no physical H200 timing or challenge score.
