# V82 compact projection of committed draft-context rows

V80 permutes all target hidden rows into acceptance order and projects every row through the DFLASH context linear. Its prefix-valid writer ultimately publishes only the rows retained for each request. V82 reads the accepted-node permutation directly and evaluates this expensive linear on compacted tiles. The target already computed and verified every proposal. Its predictions, accepted path, resulting token sequence, cache slot permutation and request lengths keep their existing semantics.

The plan is computed on device from live commit lengths. For each live destination row, it records its original target node and destination index. A BF16 tiled GEMM reads original features, traverses the complete input dimension, accumulates in FP32 and stores BF16 results directly to the dense local projection output. Tiles beyond the live count return before reading weights. The last partially filled 16-row tile still issues its matrix instructions. Inactive destinations have defined zero values. V80's draft TP gather, hidden RMSNorm and prefix-valid cache writes consume this output. The worker's existing stream event follows all cache writes. There is no inter-request output caching or host read of the committed count.

At 16 users, width eight and four committed rows per request, TP8 has 64 live rows of 128. The 40,960-by-1,024 local dot products then require an estimated **5.37 billion fewer FP32-accumulated multiply/add FLOPs per GPU per pass**. The 10 MiB BF16 full-feature permutation also disappears. The 80 MiB local weight shard, dense projection all-gather and later KV construction remain. If all candidates are committed the entire GEMM is required. Tile quantization, 640 sequential K tiles per CTA, low occupancy, redundant weight fetches, dense output zeroing and first-use compilation may erase the expected benefit. This addresses one draft phase and has no measured end-to-end speedup.

## Applicability and testing

Use V80's seven flags and add `--flag speculative-dflash-compact-context`. This path requires a live selector tree, V80's output-sharded context linear, BF16 SM90 inputs of compatible shape, a bounded prefix plan, and the prefix-valid writer. Sparse work is worthwhile only when several row tiles can be eliminated. The kernel uses a four-tile minimum. For native width eight, one and four users remain on the inherited dense path. Deterministic execution, ordinary prefill, sampled requests, unsupported backends, and other models follow their existing projection route.

Frozen [official patch](patch.diff) SHA-256 `669689a36ae624158cf3706a061d0605eaa982cfcf62e4d16c1de6ac21e1b9d7`, 155,741 bytes across 29 permitted files. The [four-file delta](delta.diff) is relative to exact V80 `11a1995768ccc8419fe17caea989b27352596eb533ac73ec24d7df03b5a3e9c6`.

The [CPU kernel check](cpu_check.py) executes the production planner and projection with checked pointers. It passed 175 row maps, 36 numerical projection cases with rejected input rows poisoned, and 19 dispatch fallback cases. The [independent review](independent_review.md) also exercises the full reduction width. H200 compilation, numerical agreement, later turns, memory, TTFT and serving throughput require comparison with V80 at the same load.
