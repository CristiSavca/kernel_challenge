# V113 two-dimensional sequence-parallel QKV prefill

V113 starts from scored V64 and changes the target’s dense Q/K/V/output-gate projection on long prefills. V64 first gathers the complete BF16 input on each GPU because every rank owns different output channels. V113 groups the tensor-parallel ranks into two halves. Each rank receives the token rows in its own half and the opposite rank's QKV weight shard. It runs the selected unquantized BF16 linear backend twice using the complete hidden width, then exchanges the opposite rank's projected rows. Its global output contains the original head channels in the original token order. The downstream QK normalization, gate, attention, O projection and all decode paths keep their native inputs. [Source delta](delta.diff)

At TP8 the target has 8,192 input channels, 16 query heads and two KV heads per rank at head dimension 64. The full 2,304 output channels include the gate. For a 16,384-token prefill the original ring all-gather sends 224 MiB per rank per layer. The new grouped sends total 168 MiB: 96 MiB of activation shards, 36 MiB for the opposite weight and 36 MiB for the result. Each rank also receives the same amounts. This saves **56 MiB per rank per layer, or 3.39 GiB across 62 layers**, while preserving the same 0.618 TFLOP per rank per layer. The layout is activated only when its predicted byte count is at least 12.5% lower. V113 estimates 272 MiB of named temporary tensors at this shape versus 328 MiB for the original path. Neither estimate includes NCCL/GEMM workspace or graph allocator residency. [Geometry](geometry.json) · [Native QKV dimensions](../../../muse_decode_layer/reference.py)

One CPU-group vote during construction checks the peer communicator, rank ordering, Hopper architecture and unquantized frozen weights. A small PyNCCL warmup establishes the same peer connections used by the CUDA graph. Runtime uses two grouped sends and receives on the current device stream. The operation supplies a fake output for compiled and captured prefill. Supported body graphs can capture the operation. Unsupported devices, dtypes and deterministic settings retain the original implementation. The candidate uses V64’s four flags. [Official export](patch.diff) · [Validation](validation.json)

The CPU suite executes the column-parallel entry and the actual paired operation with real Gloo TP4/8 peer traffic. It checks output order, padding, strides, rank-local startup failures, full-width BF16 reductions and both GEMM dispatch branches. A separate fixture exercises all 8,192 input and 2,304 output channels. The registered fake operation returns the expected shape for a 16,384-token batch. Independent review traced the peer pairs and pinned communicator's current-stream behavior. [CPU results](cpu_result.json)

V64 measured 1.4119× overall. These communication counts do not establish a model throughput speedup. NCCL's achieved P2P bandwidth, GEMM shape selection and last-bit rounding, graph residency and peak memory require an H200 check. The measured parent already used 1.9 GB of the 2 GB per-GPU allowance.
