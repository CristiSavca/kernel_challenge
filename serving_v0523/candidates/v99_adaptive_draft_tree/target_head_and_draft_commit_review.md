## Target vocabulary head

The target needs the exact greedy winner at each visited node, including a bonus at the last visited node. V91 computes the full local head for all nodes, then reduces each row to one global winner. An exact alternative could first score interior nodes, walk the tree, then score only the selected leaf for requests that reached one. Requests using sampling, grammars or logprobs would retain the incumbent, as would deterministic execution and unsupported distributed or graph layouts. Both passes would need the same target FP32 projection contract, scale, softcap tie behavior and global winner convention. Checking only the proposed child IDs cannot establish a winner over the complete vocabulary. [Target selection](../v91_reduced_target_argmax/README.md) · [Acceptance code](../v100_paged_tree_verify/patch.diff)

Each rank owns 25,256 vocabulary rows of width 8,192. Its BF16 head weight is 394.625 MiB. At 16 users the full 128-row GEMM accounts for 52.97 GFLOP and 12.33 MiB of FP32 logits. At 32 users that becomes 105.93 GFLOP and 24.66 MiB. A cold second traversal of the weight costs about 86 μs at the H200's 4.8 TB/s specification before the second TP decision. A graph-compatible implementation could gate the leaf kernel on device when no request qualifies. Native V64 has exactly one leaf per chain, limiting the saving to one row out of eight when every request stops early. V99 can choose chain-shaped requests too. I would keep the single-pass target head for the measured baseline and prioritize a GPU profile before pursuing the two-pass variant. ## Draft KV writes

Five target taps of 8,192 BF16 features feed one draft context projection. V82 already compacts accepted inputs for eligible tree batches. The worker then gathers the sharded output, normalizes it, and on the eligible stacked path executes one BF16 projection for **all five** draft layers. This projection is 8,192 × 1,280 on each rank, or 20 MiB of weights. A single Triton kernel produces normalized and rotated K and raw V in BF16 workspaces. The worker's callback then invokes five separate prefix-valid KV writers. V100's physical-slot compaction and WAR publication occur around this sequence. Existing source requires the callback to preserve physical addressing and storage conversion. The run log does not identify its fraction of serving time. [Compact context projection](../v82_committed_draft_context/README.md) · [Stock stacked helper](../../sglang/python/sglang/kernels/ops/speculative/fused_kv_materialize.py) · [Stock worker](../../sglang/python/sglang/srt/speculative/dflash_worker_v2.py) · [Pool writers](../../sglang/python/sglang/srt/mem_cache/memory_pool.py)

A concrete experiment would keep the stacked GEMM and write the existing norm/RoPE kernel's results directly to each layer's physical cache. It can use the device-side commit length before reading a discarded row. At 16 users with four commits this removes 320 KiB of BF16 workspace writes, approximately 160 KiB of valid-row workspace reads, and five kernel launches. Preserve the BF16 rounding boundary for K before any FP8 conversion, V storage scaling, per-layer physical addresses and buffer lifetimes. Restrict the initial implementation to supported pool and head layouts. The launch saving may matter more than the bytes. A matched H200 trace of stacked GEMM, norm/RoPE, prefix-valid writes and inter-step idle time would establish its priority.
