# V230 writes prompt expert inputs directly from peer GPUs

On an eligible long sequence-parallel prompt, V230 removes the full-width all-gather of pooled expert inputs. Each rank publishes its contiguous BF16 token shard. A token with any local expert routes is read once per feature tile from its owner, then written directly to each stable, expert-sorted W13 destination. Empty consumers still publish their own shard and retire it with every peer. V229's W13, gated activation, W2, weighted expert finalizer and dense return reduction consume the same routes in the same order. [Five-file delta](delta.diff) · [Cumulative official patch](patch.diff)

For a 16,384-row prompt on eight H200s, the parent materializes a 128 MiB pooled tensor per rank. With eight distinct experts drawn uniformly from 256, a rank needs 66.18% of the source tokens. The modeled remote payload falls from 112 to **74.13 MiB per rank per sparse layer**. The sorted output still contains 128 MiB of BF16 rows on average. The new transport adds a 16 MiB local shard copy, a small eligibility collective and two device barriers. Effective NVLink bandwidth, remote-load behavior, cache locality and routing skew determine the elapsed-time result. V179 first read peer inputs into a separate compact token array. V230 writes directly into the input consumed by W13. [Traffic and trace model](work.json) · [V179 transfer](../v179_peer_prompt_inputs/README.md)

The physical eight-H200 V41 chronology had 75 grouped-size prompt calls at 16 users and 150 at 32. On those traces a 5% whole-trace throughput improvement would require about 1.69 ms and 1.56 ms saved per eligible layer respectively. As a sensitivity check, 37.87 MiB takes 0.20 ms at 200 GB/s. No physical measurement of V230 supports a 4× claim. [Underlying timing and assumptions](../v197_grouped_prompt_gate_up/independent_reach.md)

The path requires a unanimous startup check for the public Hopper symmetric-memory mechanism. Each layer rechecks ordinary grouped-Humming eligibility, including local hooks, using a vote before the native route-count host synchronization. A veto restores the dense gather and original expert module on every rank. Breakable graph capture records an eager callback with fixed operands and output, so replay recounts the actual routes. Full graph capture and short forwards use V229. With 4,096 hidden features at TP8, the independent workspace is 16 MiB when configured for 16,384 rows and 16.25 MiB when both scheduler and graph back 16,640 rows. Its 17 MiB ceiling remains in effect for larger configurations. The allocation stays resident outside prompt execution. Six SM90 compilations used zero spill bytes. The 4,096-feature, top-eight kernel used 22 registers, with one set of source loads feeding all eight possible stores. The Triton CPU interpreter compared 8,632,042 BF16 words across 60 fixtures. All 65,536 bit patterns, duplicate route destinations, no-read tokens, ragged owners and guard ranges passed. Separately, real Gloo groups at TP2/4/8 ran the production SP entry, grouped adapter, route mapping and workspace lifecycle in 112 rank-cases. All 4,353,728 returned BF16 words matched. The distributed test models CUDA streams, peer addressing, GEMMs and finalization on CPU. Peer access, CUDA graph execution, rank contention, memory limit, token agreement and throughput still require physical validation.
