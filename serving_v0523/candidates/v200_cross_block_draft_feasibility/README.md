# V200 · Can the next native DFLASH block run before target verification finishes?

**The full-accept path still needs the target’s next token and all five current target taps.** V198’s native eight-row verifier receives one known anchor and seven proposed tokens. A perfect proposal verifies all seven and emits an eighth token chosen by the target head. That bonus is the next block’s anchor. The target also produces hidden features for the confirmed eight inputs. The draft projects those features to KV before its next attention forward. A full-width match resolves the next prefix length but leaves both inputs to that forward pending. V200 records a feasibility result; it has no serving patch or check reservation. ## Two independent dependencies

The fixture reconstructed the immutable V198 worker, verified the order of its normal decode entry, and executed the pinned greedy acceptance and commit functions. Nineteen paired synthetic requests had the same seven draft tokens and full acceptance, yet two possible target predictions on the eighth row produced different bonus tokens and BF16 embeddings. A second fixture kept the bonus and the first four tap blocks fixed. Changing the fifth tap changed the result of the native `DFlashDraftModel.project_target_hidden` method, and it changed all 152 subsequent attention-query outputs in a BF16 example. The checkpoint’s layer-59 tap is a necessary input to its dense context projection. The constructed weights and requests demonstrate a dependency, not its frequency on the judge. [Native execution and line references](check.json) · [Last-tap and graph ownership analysis](../v140_decode_overlap_feasibility/README.md)

The scored worker uses a folded draft graph and the ordinary TP group on the same eight GPUs. Its verifier consumes graph-backed auxiliary hidden storage, materializes the committed rows, and publishes the next anchor and length. Launching a second replay before those inputs are ready would require a separate speculative anchor, provisional KV/tap storage, an ordered commit or discard, and protection against reusing graph I/O or request slots. Stochastic sampling additionally needs the ordinary random-state ordering. Running the next native forward exactly with the now-confirmed bonus and projected KV remains possible at the existing handoff. V184’s retry studies the rejected suffix inside the current block; it does not resolve the next bonus. [Current source hashes](check.json) · [V184](../v184_intrablock_reverification/README.md)

## Optimistic same-request timing bound

Let C denote the per-request commitment including the bonus, between 1 and 8, and p the fraction of rounds that commit eight. Then E[C] ≥ 1 + 7p. Treating the reported V64 one-user and V68 16-user mean of four as exact gives **0 ≤ p ≤ 3/7**. Both endpoints are attainable. Assuming independent identical token matches gives a full-hit probability of 18.64%. The published aggregates do not establish independence. Under independent requests at 16 users, even using p = 3/7 gives a probability of only (3/7)¹⁶ = 1.30 × 10⁻⁶ that everyone commits eight. With perfectly correlated requests that probability can still reach 3/7. [All four loads](check.json) · [V68 private receipt](../../runs/04b01f958aa5487c.json)

Suppose guesses always supplied the correct bonus and context on each full hit, the entire native draft came off the critical path on these hits, and misses incurred no extra time. If every step has the same cost and draft work accounts for fraction d of that cost, speedup is at most 1 / (1 − p × d). At d = 25% this is **1.12×** for mean acceptance four. Even at d = 100% it is **1.75×**. When costs vary, divide total draft time actually hidden on full hits by total elapsed time to obtain the saved fraction. Unweighted acceptance alone cannot bound that time share. The V64 and V68 receipts report no native draft-stage duration. [Rate assumptions, sensitivity and counterexample](check.json)

## Two exact alternatives

1. **Start only data-independent first-layer work.** From the third through eighth draft position, consecutive mask embeddings make the pre-RoPE query independent of the unknown bonus. Across the eight possible next prefix lengths, these six rows span 13 possible absolute positions. In principle a new kernel could compute softmax partials for the already committed history and later combine the correct partial with the newly verified rows. The two remaining query rows still need the same historical K/V and the true anchor. The native grouped-query attention shares those history reads across the block. This alternative can move at most about 50.3 million old-history FLOPs per request in that first layer while adding up to 1,048,064 bytes of old K/V traffic per rank and request for a separate pass. Exact lowering must preserve its window, RoPE positions, nonlinear softmax and reduction order. The 1,340 MiB per-rank linear weight banks across the five draft layers are still required. [Geometry](check.json) · [Native convolution dependency](../v114_draft_mask_feasibility/README.md)
2. **Pipeline independent request cohorts.** A draft for some requests can run independently of a target for others. The alternative needs disjoint graph I/O, stable reservations and coordinated TP collective order across eight ranks, or separately constructed communicators. At one active request there is no second cohort. At 32 users, a 16+16 split can fetch large model weights twice. Across all 27 passing archived whole-decoder H200 profiles with both verification geometries, the candidate proxy for two 16-user target passes exceeded one 32-user pass by **9.83–28.87 ms** after weighting the 46 sliding and 16 global layers. In one 2.262× whole-layer check the candidate difference was **11.506 ms** and the paired stock difference **22.786 ms**. Those tests used different benchmark shape instances, single-GPU partials, identity TP operations and replay-overhead-corrected raw medians. They do not measure an eight-GPU scheduler. A cohort implementation would have to hide enough exposed draft time to offset this target cost, any change in draft batching, TP ordering and contention. No archived draft timer supports that threshold.
