# V97 projects DFLASH context before the prefill gather

V97 changes where the draft model projects the target's five hidden-state taps during long sequence-parallel prefills. Each tensor-parallel rank temporarily gathers the full BF16 draft projection weight, uses the original full-width dot product on its own prompt rows, then shares the projected rows in their original sequence order. The DFLASH worker applies the original hidden normalization and writes every prompt row to the original draft KV positions. Target attention, vocabulary projection, verification, sampling and radix-cache behavior follow V93. One additional default-off flag, `--speculative-dflash-sp-prefill-context`, enables the option alongside V93's ten flags. [Full patch](patch.diff) · [Six-file delta from V93](delta.diff)

At TP8 and 16,384 unpadded rows, the old gathers transfer an estimated 1,344 MiB per rank. The five 8,192-channel taps account for 1,120 MiB and the projected features another 224 MiB. V97 gathers 560 MiB of weight from peers and 224 MiB of projected features, saving 560 MiB per rank. These are single-direction ring traffic estimates. The new weight tensor occupies 640 MiB per rank during the local GEMM and is released afterward. The CUDA allocator can retain its storage. Peak GPU use and operation latency depend on allocator reuse, original graph buffers and the vendor GEMM selected for the new shape.

For a projection from F input channels to H output channels, the activation transfer being exchanged for a weight transfer crosses over at H prompt rows. Dispatch therefore requires more than H rows, or 8,192 for this checkpoint. The measured V64 launch allowed 16,384-token chunks and captured the target prefill graph. Its saved server log contains startup probes and does not establish the fraction of timed batches above the cutoff. Full and Breakable prefill graphs replay the inner target body, then execute the outer target tail eagerly. V97 marks the projected capture there and propagates that marker through the graph runner's output trim. The original worker still trims alignment rows before normalization and KV writes. The option requires Hopper, the original dense BF16 DFLASH projection, matching sequence and model TP groups, and the ordinary pure-prefill capture. A host Gloo vote keeps all ranks on the same collective path if one rank has a projection hook or a runtime shape or dtype mismatch. Short prefills, decode, visible hidden-state requests, logprobs, deterministic mode and unsupported layouts use the existing path. The request-scope handle resets on return or exception. The only model weight assembled for a request is a temporary copy of the existing loaded FC shards.

Thirty distributed CPU cases used genuine Gloo collectives at TP2, TP4 and TP8. For the BF16 fixtures, the original and changed paths agreed bit for bit on target logits, projected features, normalized draft KV inputs, write positions and slots. Cases included odd tails, padded graph buckets, KV trimming, asymmetric hooks, dtype mismatch and deterministic fallback. The fixtures used small integer inputs. H200 cuBLAS can choose a different GEMM tiling for the new matrix shapes. Output agreement, allocator peak, TTFT and throughput still require an official device check. V97 changes prefill time and carries no measured decode or overall speedup. [CPU fixture](cpu_check.py) · [CPU results](cpu_result.json)
