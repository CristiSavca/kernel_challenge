# V182 feeds fused Q/K normalization and KV writes into paged target verification

V182 extends V180's 16-user V68 lineage with V136's fused verification producer. For each eligible layer, the existing Q/K normalization kernel applies optional interleaved RoPE, produces the FP8 query and writes physical K/V. The paged target-verification attention then reads this query and its original full or sliding-window cache directly. If the attention shape takes the native FA3 fallback, it consumes those same operands. The V180 live-prompt path remains active on its ordinary eligible EXTEND calls. [Complete patch](patch.diff) · [Four-file delta](delta.diff) · [V180](../v180_paged_verify_direct_prompt/README.md)

An eligible layer removes up to four launches. Over 62 layers this is up to 248 launches per verification pass. Avoiding the BF16 Q/K intermediate write and read saves 4,608 logical bytes per row per rank per layer, or 34.875 MiB at 128 rows over 62 layers. Device LUT indexing, V lanes, CUDA graphs and achieved cache bandwidth affect the time saved. The H200 reference is V68 at 17,512.9 tokens/s/GPU on 16 users. V182 has no measured H200 throughput, TTFT or token agreement. [Producer work model](../v136_fused_verify_qk_rope_cache/README.md) · [V68 hardware receipt](../../runs/04b01f958aa5487c.json)

The producer returns K=None and requests no additional cache write. Native query preparation preserves the encoded FP8 storage. The producer admits only the unscaled BF16→E4M3 case with a compatible physical pool, backend and operator configuration. Other configurations retain the conventional Q/K preparation and cache writer, including actual K/V scaling. The FP8 conversion table is generated locally from all BF16 representations, the physical bounds follow the pool's post-capture backing and reserved slot zero remains untouched. Two archived H200 attention microbenchmarks match the 16-user, eight-query-row, page-size-one verification shape. A related fused producer reduced the whole attention call by 6.72–6.74 microseconds on a sliding layer and 7.42–7.43 on a full layer. Weighting by the model's 46 sliding and 16 full layers gives 0.428–0.429 ms per pass. V68's four committed tokens and 48 tokens/s/user imply an illustrative 83.33 ms cycle. If that whole saving carried into serving, the verification change alone would give about 1.005× decode. The archived producer's conversion and V68's attention backend differ from V182. This evidence favors spending scarce experimental slots on prompt work and expert projection before promoting V182 on its launch count.
