## What the hardware shows

At 16,384 prompt tokens and eight selections per token, the 256 experts execute 131,072 routes across eight GPUs. Four archived single-H200 timing runs each recorded 16,224 routes on the one participating owner. Marlin's complete expert call took 7.188–7.394 ms. One run measured 5.831 ms for the complete dense384 alternative. A separate dense BF16 projection reference at 507 rows per expert took 2.643–2.698 ms and omitted routing, NVFP4 dequantization and finalization. These give component intensities, roughly 443–456, 359 and 163–166 ns per live row respectively. They do not time an isolated helper or the newer Humming kernel. The same H200 also exercised a Breakable CUDA graph on new routes. The two ordinary trials recorded 16,336 and 16,391 local slots. ## Work, transport and memory

The original owner assigns a contiguous suffix of one expert’s stably sorted slots to a helper. One full-K, 4,096-channel W13/W2 bank uses 24 MiB packed FP4, 3 MiB group scales and eight scalar-scale bytes. Each moved row transfers 8 KiB of BF16 input plus 8 KiB of BF16 output and 16 bytes of slot IDs, in addition to the bank. Every helper takes at most one bank and never sends another bank. Helpers return BF16 W2 rows by original slot. The canonical owner alone applies its existing output scale, post-expert RMS normalization, top-k score, slot reduction and final owner combination. Returning a rank-weighted partial directly from the helper would change that reduction. A production implementation must execute the original BF16 gate/up, scaled SiLU and down path with identical packed weights and scale conventions. This study verifies movement/finalization, not H200 matrix arithmetic. [Planner](planner.py) · [Native C++ entry](planner.cc) · [Slot-return oracle](check.py)

The planner charges padded 176-row work, a cold bank on every move, both directions of payload, setup per recipient, serialized endpoint traffic and a global planning charge. It returns the best eligible prefix of deterministic greedy moves. Tile width, costs, ownership and scratch budgets are inputs. The example assumes 165 ns per issued row, 225 GB/s per endpoint, 30 μs per move, 100 μs global overhead and 50 μs minimum saving. At those rates the 27 MiB bank plus setup needs at least 1,692 movable rows even before rounding, global overhead and receiver load. At 100 GB/s and 102 ns per row the activation round trip alone exceeds the modeled row compute. At 450 GB/s and 165 ns per row the corresponding threshold drops to 723 rows. NVIDIA lists 900 GB/s aggregate NVLink on H200 SXM. No transfer or overlap rate was measured here. The full sensitivity table spans 100–450 GB/s and 102–443 ns/row. [Cost sensitivity](check.json) · [H200 specification](https://www.nvidia.com/en-us/data-center/h200/)

The hypothetical 256 MiB per-rank scratch cap covers the bank, input, output, native-sized W13/activation buffers, slot metadata and a 32 MiB backend allowance. Modeled positive paths peak at 221–252 MiB/rank. The V68/16 judge result reports **1.7 GB above stock with a 2 GB limit**. A real implementation must suballocate from a shared arena or measure available peak headroom including the live graph, backing pool, actual vendor workspace and allocator behavior. A per-layer permanent bank reservation would multiply the footprint across 62 layers. [V68 memory](../../runs/04b01f958aa5487c.json) · [Per-rank reservation](check.json)

## Where a schedule could run

The sparse prompt path exchanges shared token-owner masks but keeps the per-expert histogram rank-local. A transfer schedule must first construct identical global counts and an unambiguous expert-to-owner map on every participating rank. For this geometry, the raw 256 int32 counts occupy 1 KiB. Count materialization, any collective and device-to-host synchronization are additional costs. Vote on all ranks' capability and workspace before any rank diverges. An immutable fallback must retain the original ordering in eager/Breakable execution. [V163 exchange](../v163_sparse_prompt_exchange/delta.diff) · [V169 histogram contract](../v169_grouped_expert_tile_cohorts/independent_review.md)

The V135/V168 budget allows 18,432 live routes per owner window at 16,384 tokens. One rank can have multiple windows while a peer has one. A collective issued inside those rank-local loops can deadlock. An executable alternative coordinates new transfers above the loops using common global token ranges, each also within the owner's native capacity. The reference recomputes the baseline using each rank's own compact 128-token windows and original token membership, then charges every additional common window's work and launch separately. An alternative asynchronous return around the original loops would require a separate proof of slot ownership, arena lifetime, retirement and bounded memory. ## Validation

The C++ planner matched the Python reference across 400 randomized count, placement, capability and memory layouts, including 353 positive plans, plus five full geometries. Its ARM64 C-ABI call measured 1.8–20.1 μs on those five fixtures. The Python loop took 2.3–7.8 ms on the larger nonempty cases. Neither timing includes a GPU fence. Across 60 additional synthetic batches with duplicate slots, masked slots, noncontiguous logical ownership, empty experts, uneven ranks and randomized arrival order, 349,968 valid BF16 slots and 18,673 moved slots matched their canonical result, including the final norm/weighted-sum oracle. [Native checks and host timings](native_result.json) · [Slot replay](check.json)
