# V108 sequence-parallel DFLASH context projection

**November 18 dispatch correction.** The prompt-projection startup check in this frozen patch rejects the registered Muse logits processor. The earlier CPU fixture used the base class and missed that distinction. V120b enables the prompt optimization for the native model and tests both classes. [Correction and regression](../v120b_native_muse_prompt/README.md)

This candidate starts from scored V64, job `abd217baf0ed49fd` (1.4119×). V64's longest prompt chunks gather five BF16 hidden-state vectors for every token, then perform the same dense draft projection independently on eight GPUs. V108 runs the existing replicated BF16 linear layer on each rank’s sequence-parallel token shard, and gathers its 8,192 output channels in rank order. All 40,960 input channels participate in each dot product. The worker applies the original normalization after restoring global token order, then writes every original target position and draft KV slot. There is no new model weight allocation, weight communication, prompt-result reuse or context pruning.

With 16,384 tokens, the full all-gather tensor per GPU changes from 1,280 MiB to 256 MiB. Counting only the data sent by one rank in an ideal eight-rank ring gives 1,120 MiB versus 224 MiB. Each rank also receives the same amounts. These are tensor sizes and a communication model, respectively. The projection requires 11.00 TFLOP per GPU on V64 and 1.37 TFLOP on V108 for the same full chunk. The replicated 640 MiB projection weight already exists on V64. The original local tap rows are released after their projection. CUDA allocator peaks and physical NVLink traffic require measurement.

V108 enables this path using V64's four flags and `--speculative-dflash-sp-prefill-context`. Pure EXTEND with at least 128 token rows per rank amortizes the extra CPU-group capability check and local launch. Target/draft TP must match without PP, DP attention or context parallelism. The original path handles short shards, sampling decode, external hidden-state capture, hooked/compiled modules, deterministic mode, and unsupported draft layers or devices. A rank-wide Gloo vote coordinates dynamic instrumentation before selecting the widths of GPU collectives. The body-only prefill CUDA graph retains its original outputs; the outer eager tail performs the new projection and replay trimming carries its output format to the worker.

The CPU tests exercise the production path with real BF16 tensors and Gloo processes at TP2, TP4 and TP8. They check 69 data-path cases plus startup eligibility, rank-asymmetric fallbacks, captured-row trimming and noncontiguous cache slot identities. An additional 40,960-wide dyadic fixture matches the replicated BF16 result bit for bit at all three partition sizes. Independent source review confirmed the official DFLASH2 checkpoint uses the eligible dense layer and the Full/Breakable graph runner executes this part of the target model eagerly.

A matched V64 H200 private check at 16 users would test the predicted high-load benefit. V64 reached 1.5919× its stock frontier there with 92% cache hits. The existing score and cache-hit figures cannot establish a V108 speedup. GEMM shape selection can affect BF16 last-bit rounding, and Gloo agreement adds host latency. End-to-end throughput, H200 output agreement, TTFT and the 2 GB per-GPU peak limit remain unmeasured for V108.
