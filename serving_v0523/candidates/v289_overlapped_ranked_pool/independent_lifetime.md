# Independent peer-stream plan check

V289's route planner can run before the pooled activation arrives. The side stream reads router IDs and the layer's expert map. The only side-stream use of the packed pool is an eligibility check involving its shape, view, dtype, device, contiguity and pointer alignment. The capture vote has already attempted the rank-major module build. The actual kernel that reads the packed BF16 data runs on the main stream after both the column gather and the router join. [Production hashes and inspected calls](independent_lifetime.json)

The four plan buffers are allocated on the main stream before the side stream waits on it. This orders the planner's side writes after any prior main-stream use of memory just reclaimed by the graph pool. The main stream waits for completion of the side planner before it consumes or drops the buffers. The accepted tuple holds the plan through expert execution. A rejected local rank-major plan leaves V284's ordinary alignment, routing and join in place. Across 34 staged capture and fallback calls, each executed exactly one plan. [Parent and candidate replay](replay.json)

The independent replay models two executions reusing the same addresses. Across all nine schedules allowed by the recorded dependencies, the consumer sees the current plan and gathered data. Without the fork, 42 of 81 schedules admit a late write by the previous allocator owner. Without the main join, 72 of 81 consume the wrong plan. Making the side eligibility check read gathered data creates a race in five of nine schedules even with both waits present. These are scheduling witnesses.
