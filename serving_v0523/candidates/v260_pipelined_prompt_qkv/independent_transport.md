# V260 communication and graph review

The V260 patch uses the existing tensor-parallel PyNCCL communicator. It first issues one grouped exchange inside each logical half of the ranks on the main stream. A second grouped exchange sends each completed half to its opposite rank on the transfer stream. Every send has one matching receive with the same element count and BF16 type. At TP8 and 16,384 rows each rank sends three 32 MiB shards and one 128 MiB half, and receives equal volumes. The topology has two communication phases and one communicator. Its performance advantage depends on the overlap of the 128 MiB exchange with the first half's projection. NCCL chooses the physical transport and protocols. [Patch](delta.diff) · [NVIDIA NCCL grouped P2P semantics](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/usage/p2p.html)

The independent receipt executes the pinned PyNCCL communicator's actual send, receive, group and stream-resolution methods. A recording library at the NCCL ABI verifies buffer offsets, peer ranks, dtype, exact payload size, matching and active streams on 324 directional transfers over TP4, TP6, TP8 and TP10. The native fast stream resolver caches the worker's device index and reads its current stream on every NCCL call. The breakable capture hook records the fork in its actual tracking set and removes it at the join for every rank. Eager and full-capture contexts take its unhooked branch in the host fixture. The complementary Gloo test executes the full custom operator and checks outputs and the exceptional join. [Native ABI fixture](independent_transport.py) · [Receipt](independent_transport.json) · [Gloo execution](exchange.json)

Both temporary half-buffers and the result are allocated on the main stream. The transfer stream waits for the local cohort's writes. The main stream subsequently waits for the transfer stream in a finally block before reading the remote tensor or releasing either allocation. The owned half is read by both streams after its initial writes. The local input, projection weight, projection results and any dense-dispatch output temporary stay on the main stream. The source has a complete fork and join within the single operator. Native breakable capture can therefore close its QKV-containing segment with an empty side-stream tracking set. V68 recorded NCCL 2.30.7. That release supports graph capture of P2P groups and requires all participating ranks to agree about capture and replay. The normal worker topology starts one scheduler process per GPU. Individual peer groups each use a single stream. Actual capture, graph deduplication, replay across mixed batches and NCCL workspace peak need a physical 8×H200 run. Muse's QKV gate inherits ColumnParallelLinear.forward. Its SP entry sees EXTEND in an eager prompt or a captured prompt body. Combined DFlash batches copy the prompt batch's mode, so their verification tails also travel with that body when the complete batch is eligible. Pure TARGET_VERIFY and DECODE forwards bypass this SP entry. BREAKABLE and FULL are both body-capture backends. The V256 policy adds its extra mixed graph sizes only with BREAKABLE prefill and FULL decode. The mixed-target planner itself accepts an existing FULL prefill body if its installed keys, request slots, token capacity, and all other native checks admit the complete batch. For real TP8 QKV width 2,304, the half needs at least 576 rows per rank. At a padded size of 4,608 the first 4,601 real rows already reach that geometry. Graph bucket padding can move an input over that threshold earlier. [Native SP and graph guards](independent_transport.py) · [Parent flags](validation.json)

Archived server information selected the auto BF16 backend. On SM90 this uses native dense linear. The alternate explicit GEMV backend also reaches dense linear for both unsplit and half prompt geometries. The native dispatcher produced that decision on 11 relevant shapes. The Hopper GEMV predicate requires M=1 and the CuTeDSL backend requires Blackwell. For default auto, V260 writes two dense matrix products directly into contiguous halves of the final buffer. cuBLAS may choose different algorithms after changing M. Token agreement on H200 remains unmeasured. Forced GEMV may also create a temporary half projection and copy into the result. At TP8 and 16,384 rows this temporary occupies 36 MiB. [Backend fixture](independent_transport.py) · [Archived server configuration](../../../experiments/modal_node/20261113T204343Z-bench/results__20261113T204343Z-bench__v41__server_info.json)

For scale, at an assumed 450 GB/s per direction, the 128 MiB exchange would take 0.298 ms. At the H200 SXM dense peak of 989.5 TFLOP/s the coincident projection would take 0.313 ms. These are isolated peak-rate calculations. Effective one-peer bandwidth, link topology, the baseline all-gather algorithm, GEMM occupancy, collective CTA competition, a second GEMM launch and the repeated 36 MiB weight read can all move the result.
