# V196 · Pipelined runs of verified FP8 history tiles

V196 extends V195’s target verification attention so a gap in one tile no longer sends a long request/partition intersection through indexed loads in its entirety. The existing metadata kernel has already certified which complete 128-row physical KV tiles are consecutive. V196 reads those certificates on the GPU and selects maximal runs for native Hopper TMA. The exact official patch is 187,737 bytes, requires V195’s five flags and has no hardware serving result. [Manifest](validation.json) · [One-file delta](delta.diff)

## Dispatch and arithmetic

A short intersection of up to 32 tiles fits one 32-lane vote and keeps V195’s all-direct or all-indexed decision. Longer intersections use a sequence of 32-bit masks. The scanner sends a maximal run of at least four good tiles to the dedicated TMA loop, then sends all intervening tiles to the original indexed loop. The scanner looks at the final three tiles of the preceding word again when qualifying the start of a run, including runs beginning at bits 29–31. Address bounds and sink detection apply when each mask is constructed. Dispatch depends on the current intersection length and its physical addresses. All batches use the same rule.

Both loop bodies consume tiles in increasing logical order. The FP32 row maximum, softmax sum and value accumulator are handed directly from one run into the next. The existing QK, causal mask, probability conversion, PV, partition merge and scale handling are intact. The release verifier checks that the complete inner tile loop has the same syntax tree as V195. The certificate producer, physical descriptor checks, native fallback, prompt/expert compute and launch flags are byte-identical. [Reconstruction check](verify.py) · [Independent source and VMM review](independent_bindings.json)

## Validation

* Eight production CPU interpreter replays exercised segments of 1–98 tiles and 66 transitions between direct and indexed loads. All 40,960 FP32 partial components, 640 FP32 log-sum-exp values and 24,576 BF16 outputs were bitwise equal to V195. A separate dense attention calculation checked another 1,536 output components. The test corrects the CPU interpreter’s raw-BF16 NumPy dot handling for both implementations. [Numerical fixture](interpreter.py) · [Receipt](interpreter.json)
* The production run planner matched 1,272 decisions in the Triton interpreter. A separate source-bound oracle checked 4,621 sequences, 291,768 classified tiles and 395,551 bounded certificate accesses. [Independent boundary oracle](independent_run_scan.json)
* The local compiler built and disassembled 38 SM90 specializations. All 12 aligned V196 configurations at batches 1, 3, 4, 7, 16 and 32, with and without K descales, emitted four static machine TMA load instructions and had zero spills. The intentionally unaligned specialization at batch 16 recorded 32 spill-store bytes and 44 spill-load bytes. The 16/32-user aligned maximal-run specializations used 242/219 registers versus 239/216 for fixed groups of four or eight, all with the same 57,624-byte shared footprint. Fixed grouping leaves more valid tiles on the indexed path. [Compiler and disassembly](sm90.json) · [Alternative lowerings](lowerings)
* The official full export and the V195-relative delta independently reconstruct the same tree in either direction. [Official patch](patch.diff) · [Validation manifest](validation.json)

## Estimated reach and remaining measurement

An independent simulation ran the pinned DFLASH allocator, two-block reservation, CPU scatter, deferred host settlement and retirement on recorded public V41 client sizes. It covered 7,072 reservation rounds per initial layout, with 91 first-step and 347 sampled later batches. At 16 users with a fresh free list, the share of logical tiles admitted for direct loads rose from 36.67% to 95.94% on first steps and from about 44.4% to 95.63% later. At 32 users the corresponding shares rose from 3.81% to 96.69% and from 9.0% to 96.42%. With shuffled 4,096-row free runs, later 32-user coverage rose from 2.8% to 94.20%, averaging 6.99 accumulation runs per intersection. With 32-row churn both versions had zero direct coverage. Actual H200 physical addresses were not recorded. These are allocator sensitivities, not observed service coverage. [Native allocator replay](independent_serving_allocator.json)

The four-tile minimum trades setup and drain overhead against the opportunity to use a pipelined physical read. Identical full K/V bytes still have to be consumed. Repeatedly entering the inner loop may cost more than it saves on some fragmented histories. H200 attention timing, end-to-end serving throughput and a four-load score are unmeasured. V195 is the matched direct control. [Standalone H200 attention context](../v192_affine_verify_tiles/hardware_context.json)

### Repeating the kernel checks

Place the applied V196 kernel in a scratch directory as `paged_verify_attention.py` and the V195 kernel as `prior.py`. With Triton 3.8, NumPy and ml_dtypes available, run `TRITON_INTERPRET=1 python interpreter.py SOURCE_DIR PATH_TO_SERVING_RUNS`. A third positional argument writes an actual 256-word BF16 output witness from a mixed indexed/TMA case. To reproduce all 38 Hopper assemblies, run `python compile_sm90.py SOURCE_DIR PATH_TO_SERVING_RUNS PATH_TO_CUOBJDUMP`. The alternative source diffs are bundled beside the script.
