# V152 mixed prompt and speculative verification reference

One causal target pass can advance a live prompt chunk and verify all eight native DFLASH input positions of every decoding request. A CPU reference implementation reproduces the outputs, physical KV destinations, next bonus and next logical prefix lengths of separate executions. V147 has no complete production entry point for this operation. The available V41 hardware trace makes CUDA graph support essential. This research package is unsubmitted and carries no measured serving speedup. [Reference implementation](native_reference.py) · [Results](native_reference.json)

## Production contract

1. **Admission and reservations.** Preserve the two request sets and their order before merging. Subtract eight target rows per eligible running request from the actual graph token budget and retain the normal decode memory check. DFLASH already allocates two width-eight blocks of headroom. On V147 page one, the eight positions after the prior published base remain backed even if the previous step advances all eight. The CPU fixture tested 405 reserve and host-lag combinations. Distinguish this allocation bound from the visible prompt attention length. The existing PrefillAdder charges only one row per running request.
2. **Resolve and propose.** Keep each surviving tail's request-pool identity until the prior publish event resolves its current bonus and base. Build a tail-only DFLASH proposal using the production width, sampling metadata and TP group. Append the native draft tokens after real prompt tokens. Run all ranks with the same cohort. Preserve physical full, SWA and draft write mappings. The existing mixed resolver replaces one cache location and appends one bonus per tail, then clears its mixed indices.
3. **One target body.** A prompt of length Q sees its prefix and Q inputs. A verification tail of width W sees its published prefix and W candidates under the same bottom-right causal rule. Reuse EXTEND FA3 query offsets, absolute positions and per-request windows. Keep a separate role map through ForwardBatch and graph replay. The scored configuration enables prefill LayerNorm SP and explicitly rejects enable_mixed_chunk. Breakable replays with a static EXTEND view, full graph calls the outer eager tail with the original batch mode, and eager MIXED does not enter runs_sp. Every ranked body and eager tail must use the same shard ownership and row count at replay, including TP padding, gather and tap trimming.
4. **Exact head rows and taps.** Preserve full DFLASH taps for every real target input. A prompt contributes its final logit row, a tail contributes W rows. Select those rows after the SP gather and before the native complete vocabulary projection. Size the logits output for that distinct count and pass only prompt heads to the ordinary prompt sampler. With a four-row prompt and two tails, incumbent MIXED selects rows 3, 11 and 19. Verification needs row 3 and all rows 4–19. The shared graph buffer requests three rows. The full-graph trimmer keeps three even if 17 have been produced. The breakable trimmer preserves all 17 when supplied. The existing graph path alone cannot provide the missing heads.
5. **Settle, publish and store.** Run native target verification on all W predictions, preserve the existing TP acceptance/bonus sync, then publish real prompt lengths and each tail's committed length. Write all prompt taps and only the accepted prefix of tail *input* taps to the draft cache. The newly sampled bonus starts the next step. Native prefill publishes the full submitted sequence length, copies all input taps and settles one output per request. Host-side mixed processing needs two logical subresults. Preserve chunk completion, logprob/grammar/stop handling, output limits, retraction, release and radix checkpoint ordering by retaining the native result handlers for the respective roles. Fully unsupported batches should take the original separate forwards.

## Executed checks

The fixture uses five synthetic BF16 layer boundaries, a full-vocabulary projection, FP8 E4M3 target cache, independent full/SWA physical mappings and five BF16 draft projections. The packed single-pass attention was cross-checked against the pinned SGLang CPU TorchNativeAttnBackend 320 times and compared with separate request executions. All 64 randomized/reordered batches passed, including 224 verified tails and every committed width from one through eight. The native host result parser settled all 1,008 accepted tail rows. Poisoning 784 rejected rows preserved the next target output. Accompanying tests ran the pinned mixed batch merger, overlap resolver, graph output trimmers and logical allocator. Synthetic target reference accumulates SDPA in FP64 and rounds at each BF16 boundary to isolate masking and settlement correctness. Hopper FA3, checkpoint weights, real folded draft graphs, multi-GPU SP, scheduling performance and quality remain unmeasured. The test constructs deliberate proposal errors solely to exercise every acceptance length. [CPU receipt and exact function identities](native_reference.json)

The first deployable treatment would keep the existing draft graph, implement the replay-aware mixed row map and both result consumers together, and initially use the measured cap without shrinking real prompt chunks. A throughput comparison needs BF16/FP8 numerical gates, useful work at graph padding boundaries and actual per-load timing. There is no independent one-user gain from this mechanism in the historical trace.
