# V294 · Live prefix reuse and long-prompt sliding attention

The ten completed cold waves from V41 and V44 contain 298 prompt forwards. Fifty-two combined two cold prompts. **Zero combined forwards contain overlapping query positions or overlapping logical sliding-window key positions.** In the separate V291 candidate, both the FP8 prepacker and the native attention fallback already begin at the exact left window boundary. Neither proposed change justifies a new serving patch or an H200 check. [Cold trace](trace.json) · [V291 and FA3 replay](window.json)

## Why the two requests cannot share target rows

The native scheduler extends its unique unfinished prompt before admitting a new request and matching the new prefix in the radix tree. Every incoming prompt in these logs exceeds the 16,384-row chunk cap after its native prefix hits. Every two-request forward increases the running count by one on the next report. The earlier request therefore finishes in that forward and the incoming request starts. Native continuation and admission source hashes match both measured builds. The replay reconciles every completed cold request against both the server and client counts. V44’s partial higher-load sections have no completed client rung and are excluded. [Replay and assertions](trace.py)

If the older prompt has length L and contributes its last t rows, its first query position is L−t. For a newcomer with p cached prefix rows and n new rows, its exclusive query end is p+n. Their query gap is therefore L−p−(t+n). The logs report p and t+n for the boundary. Using the shortest actual prompt for L gives a conservative lower bound without requiring a request ID or the exact split t. Sliding attention extends the older request’s band backward by at most 2,047 positions. [Reconciled bounds](trace.json)

For full attention, the older request can reach the newcomer’s already matched physical prefix if the two requests share radix ancestry. New rows receive independent physical slots. At 32 users, the sum of incoming matches bounds this opportunity at 4,500 previously cached slots across 2,460,293 cold prompt rows. One read per shared row in each of the 16 full-attention layers would represent at most 18,432,000 bytes per rank at 256 FP8 K/V bytes per row per layer. This counts distinct source payload at each boundary. FA3 can read a tile for multiple query blocks, so that figure does not bound HBM transactions. Different queries still require their own QK and AV results. Native radix already avoided recomputing the 4,500 matched rows. ## Where ordinary long-prompt attention reads keys

For an eligible single request, V291 copies only the last min(prefix, 2,047) historical cache entries and appends the current FP8 K/V. Running its actual completion function on host Torch checked 74,896 selected cached rows over 96 cases. Every expired or current page-table entry contained an invalid negative index. Ragged packing in the same V291 patch has an identical Triton source hash to V223’s 58-case interpreter run over 63,102,016 K/V bytes with poisoned table entries. [Host replay](window.py) · [Triton interpreter](../v223_batched_direct_prompt/interpreter.py) · [V291 source binding](window.json)

For the page-one fallback, FA3 computes the first legal key position in rows before it divides into N tiles. Its paged manager adds that exact offset to the page index, and the dense TMA path adds the same offset to both K and V. Native host compilation checked 773,500 split boundaries for both Hopper FP8 geometries (192×160 and 64×128), packed and unpacked GQA, single- and multi-split launches, and long histories. The left edge included zero expired rows in every case. The right edge can round up to the N-tile boundary before predication. As an example, the first CTA of a 65,536-prefix chunk begins at 63,489, even though 63,489 is not divisible by 160. Source-level page-table translations can still touch integer metadata, and multiple CTAs can read the same legally visible keys. The replay measures neither HBM traffic nor GPU time.
