# V287 runs decode after a prompt finishes prefill

V287 gives newly ready requests one ordinary DFLASH decode round while other requests continue chunked prefill. On the archived 32-user cold wave its policy would trigger 31 times. SGLang's existing one-round interval would trigger 146 times. Both offer the same first decode opportunity for each of the 31 requests that became ready before the last prompt. The difference is how often the server revisits those requests between admissions. This is a first-service latency experiment. No H200 result establishes a serving speedup. ## Cold-wave replay

The replay preserves the observed prefill sequence and its measured intervals, together with all first-request output lengths. It adds a standalone decode forward before the next prefill when the completed-prompt cohort grows. The table assumes each inserted forward takes 50 ms. The evidence includes 20, 100 and 200 ms alternatives. The pinned V64 receipt's acceptance divided by median per-user streaming rate implies roughly 20, 36, 80 and 97 ms per round at its four loads. For 32 users, the first-opportunity median moves 115.33 s ahead of the original last report under that scenario. The model dates each opportunity using the first prefill report that shows the eligible cohort, which may be a prompt interval later than actual eligibility. The public log does not say which verified output produced the client's first nonempty text. The three V44 one-user waves have the same zero-opportunity result. V41 has one repetition each at 16 and 32 users. [Replay](cold_replay.py) · [Historical first visible text](../../../experiments/iterations/20261119-serving-cold-wave.json)

The 32 clients asked for 6,826 first-turn output tokens. Completion-triggered scheduling would create 496 request-round slots before all prompts finished. Even if every native proposal earned its maximum eight tokens, at most 18 of 32 first requests could finish early on this schedule. Four commits per round permit zero through nine early completions depending on which request became ready first. The full 16-user wave admits at most five early completions under perfect proposals. Uniformly running a round after each chunk gives more follow-on service at a higher serial cost. Seven hundred twenty-nine exhaustive assignment checks establish the bounds given the unknown admission ordering. Subsequent client turns, changing batch sizes and allocator pressure would alter the real timeline. [Bounds and oracle](cold_replay.json)

## Scheduler behavior

The parent is V68, which passed the official 16-user private check. Its target and draft computation, target-confirmed tokens, predecessor causal contexts and ordinary KV ownership all run at their original precision. The scheduler already knows whether a prompt batch contains a final chunk. When the optional completion policy is active, an intermediate EXTEND batch leaves the next prefill eligible. A final chunk or a batch containing both a completed request and another partial chunk arms the native interval. A colocated PP1 scheduler with a single synchronized TP request group can use this decision. DP attention, other gathered-buffer configurations, pipeline and disaggregated serving retain their ordinary interval policy. The native minimum-running-batch threshold prevents scheduling an idle interval when the just-finished prompt has left the cohort. V118 already studied allocating a variable verification budget across requests. V127 and V131 evaluated shortening and splitting the verifier. V166 used the selector's conditional probabilities, and V200 demonstrated the next block's dependency on the target bonus and five hidden taps. V287 advances an eligible, complete native decode operation. V194 and V235 instead combine verification rows with prompt rows in one model forward. Pairing V287 with a mixed path would need measurements because an extra serial round could displace a less expensive mixed opportunity. An isolated one-user conversation offers no competing work to reschedule.
