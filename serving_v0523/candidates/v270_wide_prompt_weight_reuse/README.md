# V270 shares a larger prompt tile across two expert W2 output blocks

**Withdrawn from check selection on November 19.** Source review found that the next persistent job could multicast an activation tile into a peer while the peer was reading its previous output from the same shared memory. V274 adds a producer acknowledgement after the peer finishes those reads and fences the buffer. Use the corrected candidate for hardware evaluation. [Corrected implementation](../v274_four_block_prompt_multicast/README.md) · [Independent ordering check](../v277_multicast_prompt_gate_up/independent_fence.md)


V270 changes the down projection for grouped NVFP4 prompt experts on Hopper. Two adjacent 128-channel blocks multicast the same 256-token BF16 activation tile. Within each block, two warpgroups compute separate 64-channel output bands. Each lane expands one original packed FP4 word using its original E4M3 scale pair, reducing its FP32 accumulator footprint to 128 registers. All K4096 terms still enter the same ordered BF16 WGMMA contraction. Tail tiles use 32, 128, 224 or 256 rows. W13 and decode use their existing paths. [Grouped projection source](delta.diff) · [Humming 0.1.12](https://pypi.org/project/humming-kernels/0.1.12/)

At 16,384 prompt tokens under uniform top-eight routing, expected packed W2 weight-and-scale requests fall **22.9%**, from 929.8 to 716.6 MiB per GPU per layer, before cache reuse. The full-width compiled consumer loop falls from 1,003 to 598 static instruction sites. More blocks are needed for the narrower output tile. Weighting their consumer instruction sites by the modeled block counts and actual residual widths yields an 8.2% reduction at 16K. Both the baseline and the candidate use eight math and four producer warps per block. Static instructions omit producer time, communication, cache and tensor-core throughput effects. The eight-row comparison uses the smallest representable row quantum per expert. TMA can read past an expert's last live activation into the following packed rows or zero-fill outside the tensor. The table prices full activation boxes and includes redundant row tails. The final writer masks every inactive row. Under the 10,240-token geometry the always-wide estimate increases consumer issue work by 16.7%. The actual host descriptor chooses between two compiled W2 kernels from the local route count and number of experts. It estimates per-expert weight sweeps at the average plus and minus its square root. The resulting 32-expert ranges select the new kernel for 5,249–8,704 and at least 10,689 local routes. Other expert counts derive their own thresholds. Skewed routing can differ substantially from this uniform model. A 256-row native one-warpgroup kernel spilled 15,744 store and 15,052 load bytes. Its four-stage K loop contained 1,910 local-load instructions. V270's production image had zero stack, spills and local loads across all four live widths. Its dynamic shared-memory ELF symbol is 156,672 bytes versus 136,192 for V256. The binary includes real two-destination TMA multicast. An independent replay follows 8,192 FP4 coordinates, 2,048 scale-byte coordinates and 196,608 output half2 stores through the pinned warp and epilogue layouts. Another test matched 2,072,064 compact BF16 output words and 1,048,864 route-map entries through the actual grouped host entry using modeled accelerator contractions. The setup code queries the driver for the resident cluster count of the actual cubin with its exact shared-memory opt-in and thread and cluster dimensions. It unloads the temporary module and uses Humming's existing per-profile grid-size field. If residency is unknown or zero, setup selects a native narrow image. At 16K the uniform model yields 1,274 logical cluster jobs. With 64 pairs resident, statically launching 66 pairs can cost 38 equal-weight job intervals versus 20 for the 64-pair grid. Barriers are confined to each pair. The penalty comes from assigning a full persistent work queue to a pair that starts late. Actual job durations differ by live width and cache behavior. Real CUDA Python 13.0.3 launch structures were tested in Linux with 12 substituted driver responses, including failures during module load, lookup, attribute configuration, occupancy and unload. To reproduce, apply the official patch to the published SGLang pin. Supply an extracted Humming 0.1.12 package, the checkout and an empty images directory to `candidate.py` with a CPU PyTorch environment. The diagnostic controls are generated by `render.py` with the same arguments. Build with `compile.sh`, the vendor include directory and Hopper NVCC. The `isa.py` driver expects the diagnostic cubins, logs, disassemblies and CUDA sources under `images/` and the three production cubins, logs and disassemblies under `check/images/`. `load_check.py` takes the same first three arguments and the compiled production directory. Run `callback.py` and `shape.py` with the assembled checkout. Run `occupancy.py` with the production prompt_weight_pipeline.py path under Linux CUDA Python 13, `work.py` from any directory and `verify.py` against the pinned checkout.
