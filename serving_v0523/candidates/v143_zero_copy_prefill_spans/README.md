# V143 zero-copy FP8 prefill on page-one V64

V143 lets long full-attention prompt layers use Hopper FA3 tensor-memory loads directly from the existing physical FP8 cache. It keeps V64’s page-one allocator and four launch flags. Two GPU kernels check the **current batch’s actual physical slot IDs and live lengths**. A qualifying layer then passes an exact strided view into the original K/V storage to FA3. The native per-token cache write and prefix ownership continue to apply. The frozen patch is 55,262 bytes across 11 allowed Python files, with two changes against V64. There is no H200 score or end-to-end timing for V143. [Official export and flags](validation.json) · [Delta from V64](delta.diff) · [Scored V64](../../runs/abd217baf0ed49fd.json)

* **Dense span.** A single sequence qualifies when every physical token follows its predecessor. A batch qualifies when its sequences have equal live lengths, constant nonoverlapping physical row spacing and individually contiguous rows. The dense descriptor ends at each sequence’s last live token. This permits arbitrary physical start slots and non-multiple-of-160 lengths.
* **Virtual pages of 160.** A fragmented layout can still qualify when every logical block of 160 live keys is physically consecutive and every block starts at the same residue modulo 160. Physical pages can occur out of order and multiple requests may share live prefix pages. The new table indexes the original cache from that common residue. Each qualifying request ends on a complete tile. A fragmented partial tail goes back to the native page-one call.
* **Lifetime.** The certificate belongs to one forward’s metadata. The CPU receives six integers asynchronously and queries a CUDA event before reading them. A layer that arrives early uses the native call immediately. The request table, length tensor, actual query count, storage bounds, alignment and available tensor version counters are checked before use. The compact page table records its consumer stream. Ordinary Breakable replay creates fresh metadata per live batch. Full capture and compilation retain the native call. [Native ABI, replay and lifetime review](independent_review.md)

The change covers ordinary full causal FP8 EXTEND with queries of at least 512 tokens and a physical table of at most 262,144 entries. It excludes sliding-window attention, translated or sharded cache layouts, padded live-query mismatches, unsupported precision, deterministic modes and requests for auxiliary outputs such as LSE. The original query, output destination, K/V descales, causal alignment, softcap and split setting pass through to FA3. Each valid token is still read from its original physical address. The certificate retains no request history. ## Opportunity and measurement

V64 already computes the full draft context projection once per prompt append on each TP rank. V97 and V108 distribute its token rows across sequence-parallel ranks before gathering the projected BF16 result. V120b wires that behavior into the registered Muse model. Accumulating each of the five taps in a separate GEMM would change where the native full-K reduction rounds and would add intermediate traffic. V143 targets the separate full-attention cache read. [V97](../v97_sp_prefill_draft_context/README.md) · [V108](../v108_replicated_sp_draft_context/README.md) · [Registered model integration](../v120b_native_muse_prompt/README.md)

V64 actually launched with page size one, 16,384-token prefill chunks and unified memory disabled. A fresh empty full-slot allocator initially hands out sequential addresses. Interleaving, fragmented frees, and shared prefixes make later allocations variable. V143 proves the mapping afresh before use. The archived server log ends before per-forward layout observations; its 92% cache hit rate does not measure the percentage of qualifying spans. V95 and V137 pack KV by copying its bytes to scratch. V120b changes the physical page size. V143 uses neither mechanism. [Recorded V64 startup](../../runs/abd217baf0ed49fd.log) · [V95](../v95_v64_dense_fp8_prefill/README.md) · [V137](../v137_ragged_full_fp8_prefill/README.md) · [V120b](../v120b_native_muse_prompt/README.md)

With two 64-wide FP8 KV heads per GPU, packing one sequence of 74,160 keys would copy 18.11 MiB of K and V per full-attention layer. Across 16 such layers, a qualifying direct view avoids 579.38 MiB of logical pack-source reads plus scratch writes for that chunk. At 16,384 keys the corresponding saving is 128 MiB. Across a hypothetical new 74,160-token request processed in five eligible chunks, those copy operations total 1.82 GiB per GPU. This compares the operations to V95’s packing. V64 already avoids packing, so its potential gain comes from faster FA3 attention. Queue overlap, HBM traffic, native FP8 agreement, geometry frequency, first-turn TTFT, steady throughput and process peak remain unmeasured.

## Verification

The submitted classifier and reducer compiled into 28 SM90 binaries. Triton’s CPU interpreter exercised 243 layout cases, including invalid IDs, mixed physical residues, gaps and large prefixes. The paired V64/V143 wrapper test checked 4,096 startup conditions and 63 attention calls. It compared 19,411,200 raw FP8 bytes, 10,368 bottom-right causal output scalars, storage aliasing, three split settings, return-LSE fallback, nonblocking late certificates, capture and instrumented modes. An independent test evaluated 960 pinned native TMA configurations, 1,392 C++ shape equations, 72 changing-batch Breakable replays and 24 distinct consumer-stream cases. The CPU attention oracle and offline SM90 builds do not execute FA3 on a physical GPU.
