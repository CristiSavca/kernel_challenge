# V116 schedules sparse W13 using staged expert IDs

V116 computes a compact list of local experts once in the kernel that already stages normalized route inputs. Every W13 CTA can then look up its assigned expert directly. At 32 verification rows with top-eight routing across 256 experts and 32 local experts, V116 launches 1,536 W13 CTAs, down from 2,048 in V89 and V114 at the same shape. This is a 25% reduction in launched CTAs. The number of kernel launches and the amount of useful matrix multiplication stay the same. The H200 serving speedup is unmeasured. [Official patch](patch.diff) · [V114 delta](delta.diff) · [Validation](validation.json)

The route stager already has a histogram of local expert IDs. Token program zero preserves the ordinary offsets at the beginning of the allocation, then writes a count and a sorted list of nonempty expert IDs after those offsets. The extra capacity is `(local_experts + 1) * 4` bytes, or 132 bytes at 32 experts. The downstream Humming W2 kernel still receives a contiguous view of exactly the original E+1 offsets. Only W13 reads the appended list. The ordinary fused and separate staging paths retain their original layout and V114 scheduler. [Host dispatch verification](dispatch.json)

The host sets the Y grid using the model's expert counts and the tensor shape. For T tokens, top K distinct selections, G global experts and E local experts, the uniform occupancy estimate is `p = 1 − (1 − min(K/G, 1))^T`. The grid budget is `ceil(Ep + sqrt(Ep(1−p)))`. The second term gives a conservative dispersion margin under that model. If the budget reaches E, the adapter uses the original layout. This estimate only sets launch geometry. Each CTA walks the actual device list at grid stride, so skew, duplicate expert IDs, all-remote batches and nonuniform expert mappings preserve complete coverage. The inherited BF16 projection and FP32 accumulation order are identical at source. [Producer and consumer audit](independent_review.md)

In the 32-token uniform model, a rank averages 20.414 active experts and exceeds the 24-group budget in 5.58% of batches. At least one of eight ranks exceeds it in 38.70% of batches. The projection processes an average of 0.088 extra expert iterations per rank in that model. A deterministic pattern that visits all 32 local experts causes eight of the 24 groups to perform two iterations. Inferred occupancy does not characterize any private request or checkpoint distribution. [Exact occupancy calculation](independent_occupancy.json)

## Code generation and correctness

The complete C++ host wrapper compiled with CUDA 12.9 and the production SM90a device code assembled to a cubin. The new list consumer uses 75 registers per thread, the V114 ballot consumer uses 80 and the direct consumer uses 77. Each uses 16 KiB of static shared memory and zero spill bytes. All three fall into the same 80-register allocation class and allow six 128-thread CTAs per SM from the register budget. An earlier unrestricted list kernel used 88 registers and could allow only five. [NVCC and PTXAS results](nvcc.txt)

The frozen list consumer has no vote instructions. Disassembly also shows a cost in the hot path. The full-K inner loop contains 342 instruction sites in the new kernel, 327 in the prior direct kernel and 324 in the prior ballot kernel. All have eight HMMA sites and six global-load sites. The longer live-expert loop can offset savings from empty CTAs and dispatch. A compiler experiment with the sole replacement of the new launch bound by `__maxnreg__(80)` produced 324 hot-loop sites, 80 registers and zero spills, alongside 656 total instruction sites compared with 624 in the frozen kernel. Its cubin and five other alternatives are identified in the [compiler comparison](compile_alternatives.json). Instruction-site counts do not measure stalls, realized occupancy or kernel duration.
