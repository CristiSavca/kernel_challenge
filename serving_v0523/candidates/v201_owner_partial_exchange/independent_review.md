**Transport and graph eligibility.** The model installs the opt-in for the existing Humming/Marlin sequence-parallel expert return and attention output GEMM. Setup checks group rank order, device, backend and deterministic mode with a CPU Gloo MIN before warming the actual PyNccl peer pairs. Hot dispatch depends on collective input dtype, device family and shape. The custom op canonicalizes a strided local tensor internally, and so that stride cannot change which collective the rank enters. Each sender/destination pair derives the same live row count even with an empty final owner. The pinned wrappers use the current CUDA stream. The grouped sends, receives, reduction and subsequent reuse of the same scratch are submitted in that stream. The CPU replay verified 21,686 paired C ABI calls at 126 geometries over TP2/3/4/5/7/8/16, 936,632 wire words, 118,073 outputs including padding and all-negative-zero rows, and restored communicator state. It used the pinned wrappers with a simulated NCCL C library. Only a physical run can validate CUDA graph capture, transient pooling and peer transport time. **Floating-point contract.** The path transmits the original BF16 GEMM or expert partials, initializes the FP32 accumulator with source rank zero, and rounds the final sum once to BF16. All-negative-zero input retains its sign. For eight finite normal BF16 partials with exponent spread at most 13 and no overflow, even the sum of their absolute aligned significands fits FP32. For wider spreads the parent collective's reduction order can affect the result. For example, eight BF16 values starting with `[2^30, 1, −2^30, 1]` and four zeros yield 1 in ascending-rank FP32, 0 in a balanced FP32 tree, and 2 in exact arithmetic. These are legal ordinary reduction orders. The measured V64 log identifies NCCL 2.30.7 but does not specify the executed reduction algorithm. The optional flag retains the parent path under the pinned deterministic launch policy. The real serving correctness check remains material. **Performance threshold.** At TP8, the 4,096-channel expert and 8,192-channel attention results occupy 128 and 256 MiB per rank respectively. Against a ring all-reduce, the protocol saves 112 and 224 MiB of sends per rank, plus the same receive volume. At 450 GB/s in each direction that equals 0.783 ms per layer for both exchanges together. Applying that link-time equivalent only to the 75 and 149 full chunks observed in our V41 16/32-user H200 traces gives 3.64 and 7.23 seconds, or 2.21% and 2.38% of those runs. A 5% raw speedup from these full chunks alone would need 1.688 and 1.569 ms of actual net savings per layer. This is a conditional volume model. Native NVLS can offload the reduction, alternative collectives can use different links and algorithms, and additional partial chunks may meet V201’s threshold. Near-peak ring-equivalent byte savings alone do not establish that V201 speeds up V198. Graph memory can include the full parent GEMM result, compact output and receive stack at once, plus an input copy for unusual strides.
