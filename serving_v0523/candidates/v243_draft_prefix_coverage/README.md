# V243 tests omitting old DFlash draft KV during prompt prefill

**Retain V241's dense draft-context writes.** The released draft reads a 2,048-token window. ## How much work is exposed

The archived eight-H200 V41 trace contains 59 first requests and 708 later requests. The later requests reused 58,190,898 of 58,872,559 prompt tokens (98.84%). A model that partitions each first request's uncached rows into consecutive chunks of up to 16,384 and projects only each chunk's last 2,048 would omit 3,906,550 draft rows. The 40,960-to-8,192 context projection and five subsequent KV projections collectively account for 838,860,800 logical FLOPs per omitted row across all ranks, or 3.277 PFLOPs in this optimistic model. The request log records lengths and cache hits. It provides neither a per-kernel time nor confirmation of that chunk partition. [Trace replay, hashes and formulas](coverage_replay.json)

Every observed later request extended a cached prefix with fewer than 2,048 new tokens. To make arbitrary prefix hits safe by always rerunning the minimum preceding target context, the released FA4 draft's 2,047-position lookback would require 767,615 extra target rows. The target's 62 layers of Q, K, V and output projections alone account for 14.372 PFLOPs on those rows, **4.386 times the optimistic draft saving**. A conservative 2,048-previous-token convention gives 768,323 rows and 4.390 times. These are logical work comparisons. The true fraction of affected requests under a coverage-aware policy is unmeasured. [Window geometry](../v188_draft_window_metadata/README.md) · [Per-load totals](coverage_replay.json)

## Two cache lifetimes that expose omitted rows

1. **An earlier checkpoint boundary.** With a full-only radix match through position 8,192, the target's native SWA component publishes the checkpoint at 8,192 during a planned 16,384-row chunk. A later divergence at 8,191 passes the device validator and can also pass the hierarchical validator after host restoration. After 256 appended tokens, the next draft call can see 1,791 rows from the old branch. Keeping only the tail of the planned chunk preserves zero of them. The no-branch control rejected the same interior match before recovery. [Runnable branch and match test](coverage_replay.py)
2. **Rebinding the target SWA to retained full IDs.** Even when the initial chunk has no shortened checkpoint, another request can recompute an interior range into new full slots while the original full slots are retained. The tree can move the fresh target SWA ownership to the retained full IDs and release the incoming full IDs. V241's private BF16 draft reads those retained full IDs directly. Writing correct draft values under the incoming IDs supplies no data under the retained IDs. Across five region lengths and two allocator modes, the native Python recovery handler published correct target values in every case. All 503,360 tested BF16 words from the omitted draft rows still contained the test sentinel. The dense parent control retained every expected value. The CPU replay exercised the production Rust-to-Python action adapter. The two native Rust producer branches were source-checked. ## What would permit safe pruning

The V68 H200 service allocated 3,420,199 private BF16 draft slots, matching full target capacity. The target had 855,049 SWA slots. The separate draft host pool follows target full-slot transfers. With the same token capacities and 2,560 draft KV bytes per token per GPU, a design genuinely backed by target SWA ownership would use an estimated **6.116 GiB less logical payload per GPU**. That estimate excludes allocator overhead, host pools and any increase in the serving allocator's eventual capacity. [V68 hardware log](../../runs/04b01f958aa5487c.log) · [Slot capacity and host-backend guards](locked_recovery.json)

An implementation could give draft coverage its own device and host lifetime through insertion, splits, recovery, transfers and slot recycling, or translate all eligible draft reads and writes into the same SWA ownership domain. The pinned generic window-host placement currently requires a Triton per-step address rail. The archived serving configuration selects FA4. A private SWA sidecar already exists for models with a true SWA-backed draft pool. The current private full pool, FA4 page tables and host transfers would all need to agree on the same storage mapping. V130 and V171 retain all draft rows. V188 reduces page-table traffic while preserving those rows.
