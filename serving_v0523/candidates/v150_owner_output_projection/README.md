# V150 sends attention output to its token owners

On a long sequence-parallel prompt, V147 computes the full BF16 attention output on each tensor-parallel rank. With the default NVLS setting its row helper calls all-reduce and then keeps that rank’s token rows. V150 partitions the same projection by destination token rows and output channels. Every rank computes its full local K contribution to every destination. A second stream sends each BF16 partial directly to its owner while the next GEMM runs. The owner sums rank contributions in FP32 and rounds once to BF16. [Change from V147](delta.diff) · [Full challenge patch](patch.diff)

At 16,384 token rows, 8,192 output channels and eight ranks, each rank sends 224 MiB and receives 224 MiB per eligible layer. The 256 MiB full projection becomes two 4,096-channel stripes. The named buffers total about 192 MiB per rank during the projection, including a 128 MiB stack of partials, two 16 MiB outgoing results and the 32 MiB final output. This estimate excludes inputs, ragged padding, allocator overhead, CUDA graph pools and library workspaces. V64’s scored build used 1.9 GB/GPU of the allowed 2 GB/GPU above stock. Its physical NVLS traffic and the candidate’s process peak on H200 have yet to be measured. [V64 official result](../../runs/abd217baf0ed49fd.json)

The candidate applies only to eligible Muse output projections on Hopper. A startup vote verifies communicator availability, rank order and eligible frozen BF16 weights before initializing peer connections. The size gate requires at least 512 rows per peer and 32 MiB of unsharded output. The existing SP entry handles short inputs and incompatible modes. Physical performance depends on whether the eight peer GEMMs per stripe retain tensor-core efficiency, how effectively transfers overlap, and the incumbent’s NVLS algorithm. [Independent review](independent_review.md)

Four and eight Gloo ranks exercised the regular row-parallel entry. The fixture checked 403,188 output elements and 748 grouped peer exchanges. Triton’s CPU interpreter checked 224,712 FP32 sums before rounding, 74,904 exactly representable BF16 stores and 1,768 guard elements around strided outputs. Its implicit BF16 store truncates on the test host, so the test also inspected the compiled Hopper instructions for round-to-nearest-even conversion. The TP4 and TP8 binaries used 22 and 30 registers respectively and had zero spills. CUDA graph replay, greedy agreement, memory, first-token latency and serving throughput await H200 measurement. A separate CPU test used random BF16 matrices with local K up to 1,024. Splitting the GEMMs reproduced all 151,840 rank partials. The candidate matched a balanced FP32 sum on all 22,776 final elements. A balanced BF16 sum gave a different result on 9,707 of those elements. This makes the incumbent H200 collective’s behavior relevant to the agreement check. [Reduction order comparison](reduction_orders.json)

The official CLI exported 121,206 bytes across 18 permitted paths. The full patch and three-file parent delta reconstructed the same tree and both reversed cleanly. The candidate inherits V147’s four flags. It is a reserve and has no judge submission. [Validation](validation.json)
