# V140 decode overlap feasibility

The measured V64 worker already advances ordinary greedy DFLASH decode without fetching the committed sequence lengths to the CPU. The remaining opportunity is to start the draft context projection after target layer 59 and overlap it with target layers 60–61 and the target vocabulary head. An independent H200 projection measurement suggests this could save roughly **0.25 ms per one-user pass** if the whole projection were hidden. V64’s illustrative one-user pass period is **19.69 ms**. With these assumptions, even perfect overlap would improve one-user decode by about **1.013×**. We kept V140 as a feasibility study and spent no GPU quota. ## What the scheduler already overlaps

The V64 launch used eight GPUs, native eight-row target verification and a selector folded into the draft CUDA graph. On the unsharded FA3 backend, both target and draft permit device-only sequence lengths. With ordinary DFLASH, two-batch overlap disabled and a live future index, FutureMap gathers each request’s committed length on device. It inserts a device-stream event wait on CUDA. The CPU length mirror stays empty. The worker publishes the new lengths immediately after acceptance, then consumes the verified target features and writes draft KV. The scheduler can launch the next forward before processing the preceding batch’s CPU result. An end-of-step CPU wait may still matter if it falls on the critical path. The scorer publishes no scheduler-idle profile. [Recorded graph setup](../../runs/abd217baf0ed49fd.log) · [Worker and scheduler source check](check.py)

The fixture executed the pinned FutureMap publish and resolve methods through 512 cycles with 6,784 shuffled request positions. Its tensor and event stand-ins raise on a host read or host event synchronization. The data arrived in request order, with 512 device event waits and zero host waits. This tests the ordinary GPU-only branch. Sharded KV, two-batch overlap, grammars, synchronous scheduling and other fallback modes have different dependencies. [Fixture and receipt](check.json)

## Scale of the possible overlap

The draft projection consumes five 8,192-wide target taps and writes 8,192 BF16 channels. Its 40,960 × 8,192 BF16 weight occupies 640 MiB on each V64 GPU. The separately scored H200 projection benchmark exposes a 64 MiB BF16 pooler at the same four row counts. The proxy below scales its raw stock median by ten. The two GEMMs have different input and output dimensions, call sites, cache behavior and kernel selection. This extrapolation is a sensitivity estimate. The period divides a load-level mean commit count by median user decode rate, so it is also an estimate. The individual V64 and pooler statistics are official measurements. A hypothetical uniform 2.833× gain over V64 would move its 1.4119× score to 4× if every scored rung scaled proportionally. Achieving that same factor on the estimated one-user decode period would require removing **12.74 ms**. For the FC alone to take that long, it would need effective weight throughput of at most **52.7 GB/s**, roughly fifty times slower than the byte-scaled proxy. ## Dependency and hardware test

Native DFLASH consumes target taps after layers 1, 16, 30, 44 and 59. The target collects each tap in the operator dtype, then its logits processor packs the features and performs the native FP32-output vocabulary head. Calling a helper after target graph replay can overlap only selection and acceptance. To reach the last two transformer layers and the head, the side-stream FC would need to start inside the captured target graph at the last tap. Its consumers must wait before the graph reuses the tap or projected storage. A projected output needs an explicit marker so fallback, graph padding and raw hidden-state consumers remain correct. Actual prefix-valid KV writes still depend on target-confirmed commit lengths. [Tap configuration](../v118_native_tree_budget/README.md) · [Verification and pruning dependencies](../v131_exact_verify_pruning/README.md)

The ideal saving from overlapping two phases is the shorter duration. Both live phases compete for HBM bandwidth and tensor cores. V120b already reduces per-rank verify FC weight reads from 640 to 80 MiB by sharding output features and gathering their projected rows. If local FC time scaled ideally with weight traffic, the replicated projection would need to hide more than seven eighths of its original duration, minus the sharded all-gather time, to beat that approach. A hardware experiment with more potential would begin the **local output shard** at tap 59, preserve the existing post-target order of its collective, and compare against V120b. CUDA events around the unmodified local FC, the last two target layers, native vocabulary head, collective, and joined completion would establish how much time can be saved. V91 already reduces the greedy TP decision, while V121 and V127 document the head and fixed-width verification constraints.
